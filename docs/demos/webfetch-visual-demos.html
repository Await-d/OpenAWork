现状

原始 JSON 平铺

当前实现：状态徽章 + URL + 「N 行 N 字符」+ 原始 JSON 纯文本 + 与之重复的参数区。 技术信息与内容信息混在一层，字号 10–11px，长 JSON 被硬截断成破碎的字符串片段。

  • 零解析成本，任何接口都能显示
  • 内容几乎不可读，像调试输出而非对话
  • URL 与参数重复，视觉噪声大

方案 A

结构化识别 · 结果卡片

识别出常见接口的响应结构（GitHub 仓库 / 用户、搜索结果、RSS、通用 JSON 对象）， 把 payload 直接渲染成语义卡片：一眼看到名称、描述、语言、star 数。 顶部一行把「状态码 + 域名 + 结果量 + 耗时」压成一行，不再单列 URL。

  • 信息密度最高，扫一眼就知道抓到了什么
  • 技术细节退到页脚，只有需要时才去找
  • 每种接口要写解析器，长尾接口覆盖不到

方案 B

通用响应查看器 · 语法化 JSON

不做接口级别解析，只把 JSON 渲染成可读的树：键名 / 字符串 / 数字 / 布尔分色、 缩进引导线、长字符串省略、数组超出 N 条折叠。并自动隐藏 gists_url、starred_url 这类模板 URL 冗余字段。

  • 零接口适配，任何 JSON 接口立刻变好看
  • 保留了完整数据，可逐层展开核对
  • 仍偏「开发者视角」，非 JSON 的长文抓取需另一条路径

方案 C

对话优先 · 极简语义行

场景换成抓取网页正文。折叠态只有一行：站点图标 + 域名 + 「读到了什么」+ 状态点。 展开后是干净的正文排版，状态码 / 耗时 / 体积 / 参数 / 原始数据全部收进底部一行 「技术详情」，默认不打扰阅读。

  • 最安静，和对话流融为一体
  • 正文（Markdown / 纯文本）阅读体验最好
  • 技术信息要多点一次，排查问题时略慢

本地优先的 AI 工作台：为什么我们把状态留在磁盘上

过去一年里，我们把大部分会话状态从云端搬回了本地 SQLite。原因很直接：模型的响应速度已经不再是瓶颈，真正的等待来自往返同步——一次网络抖动就会让整个编辑循环卡住。

本地优先带来的第二个好处是可审计。每一次工具调用、每一条消息、每一个产物都落在磁盘上， 排查问题时不必再去翻服务端日志；代价是必须处理冲突与并发，这也是我们引入租约与幂等键的原因。

本文记录了迁移过程中踩到的坑，以及为什么最终选择了「先写本地、再异步回传」这条路径……

我的建议

  1. 以方案 B 为通用基线——所有 JSON 输出立刻受益，零接口适配，改动集中在 tool-output-preview.tsx 与一处新样式表。
  2. 叠加方案 A 作为高价值增强——先只覆盖 GitHub / 搜索结果这类高频接口， 命中就升级成卡片，未命中自然回落到 B。
  3. 方案 C 用于正文型抓取——Markdown / HTML 文章走极简行 + 技术详情折叠， 这块正好是现在最丑的那条路径。
