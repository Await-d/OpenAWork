工具结果可视化 · 设计稿

四个场景、各两到三个变体。数据取自代码里的真实构造处（不是编的）： 管理类工具的 action: 'list' 返回、session_read 的文本转录、渠道读取类的数组 / 信封、以及 models 的 provider 分组目录。

我的建议

  • 管理类走变体 A，因为它要和其他卡片同一套语言（首字母方块 + 状态徽章 + 次要信息行）， 而且七个工具的信息层级其实很像：标题 + 状态 + 一句描述 + 若干技术字段。 变体 B 的表格更适合「定时任务」这种天然列对齐的数据，可以只给它用。
  • 变体 C 的状态摘要值得单独做：当列表里有停用 / 失败项时， 头部一句「1 个已停用」比让用户逐行找要省事得多。
  • 会话读取走变体 A——转录卡最能还原「读聊天记录」的心智， 工具调用折叠成 chip 后长转录也不会被 JSON 淹没。
  • 渠道读取按数据形态分两条：消息 / 群组走行卡（A、C）， Bitable 记录走动态列表格（B）——字段名是用户自建的，写死列名一定会错。
  • models 建议 A 打底、C 作为可选视图：A 与管理类共用同一套行卡语言， 实现成本可以共享；C 的成本条形只在「挑个便宜的」这个意图下才有价值， 而用 models 更常见的场景其实是「确认某个模型在不在」——那种情况下 A 更快读。 三列定价的 B 表格最精确，但列一多就会把模型名挤窄，所以我把它排在 A 之后。
