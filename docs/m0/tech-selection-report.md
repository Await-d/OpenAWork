# M0 技术选型报告 — 微信小程序点菜系统

> 版本：v1.0 | 日期：2026-06-22 | 状态：已完成

## 1. 背景与目标

本项目是一个轻量级微信小程序，核心场景为两人协作点菜：用户 A（点餐者）选择菜品并提交，用户 B（接单者）即时收到通知。M0 阶段需确定前端开发框架。

## 3. 多维度对比分析

### 3.1 开发效率

- **微信原生**：无需学习框架，直接使用微信开发者工具。对于本项目（页面少、逻辑简单），开发效率最高。
- **uni-app**：Vue 语法 + HBuilderX 工具链，适合有 Vue 经验的团队。跨端能力对本项目无价值。
- **Taro**：React 语法 + CLI 工具，适合有 React 经验的团队。跨端能力同样超出需求。

### 3.2 与微信生态集成度

- **微信原生**：100% 兼容，所有微信 API（订阅消息、云开发、实时音视频等）开箱即用。
- **uni-app / Taro**：通过适配层调用微信 API，大部分场景无障碍，但边缘场景可能需要条件编译或原生混合。

### 3.3 通知方案适配

本项目核心需求之一是 A 提交后 B 收到通知。方案包括：
1. **小程序内实时通信**：WebSocket / 云开发实时数据库
2. **微信订阅消息**：跨应用通知

- **微信原生**：云开发 SDK 直接集成，实时数据库监听最简单。
- **uni-app / Taro**：需通过条件编译或原生插件接入，增加复杂度。

### 3.4 长期维护

- **微信原生**：跟随微信官方更新，无第三方依赖风险。
- **uni-app / Taro**：需关注框架版本升级、微信 SDK 版本对齐等。

## 4. 推荐结论

### ✅ 推荐方案：微信原生小程序

**理由**：

1. **项目规模匹配**：本项目页面少（点菜页、订单页、通知页），逻辑简单，无需跨端框架的抽象能力。
2. **最低技术风险**：原生开发无框架依赖，避免跨端适配带来的不确定性。
3. **最佳微信集成**：云开发 + 订阅消息的原生支持，通知方案实现最简单。
4. **最小打包体积**：无框架运行时，用户体验更流畅。
5. **最低维护成本**：只需关注微信官方 SDK 更新。

**附加建议**：
- 使用 **TypeScript** 提升代码可维护性
- 使用 **微信云开发** 作为后端（免服务器，实时数据库天然支持通知）
- 菜单数据初期硬编码或存入云数据库，后续可扩展为管理后台
