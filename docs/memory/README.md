# 长期记忆：确认写入与周期整理

本文说明 OpenAWork 的长期记忆在「什么时候会记录、记录到哪里、谁来确认」上的实际行为。目标是让用户放心：**临时操作不会被沉淀成长期记录，任何正式变更都要经过明确确认。**

## 一、三种信息不要混为一谈

| 层                    | 内容                         | 自动化程度                   | 生效范围                      |
| --------------------- | ---------------------------- | ---------------------------- | ----------------------------- |
| 会话摘要 / 上下文压缩 | 当前任务的进度、结论、待办   | 自动                         | 当前会话                      |
| 长期记忆              | 稳定偏好、项目事实、长期约定 | 自动生成**候选**，确认后入库 | 个人 / 项目 / 团队 / 渠道对话 |
| 规则                  | 必须遵守的行为、流程、约束   | 生成建议，确认后生效         | 指定作用域                    |

关键点：**会话摘要不会自动晋升为长期记忆或规则。** 压缩上下文是为了让当前会话能继续聊下去，不是为了替用户记住什么。

## 二、什么会被问、什么不会被问

系统只在「可能具有长期价值」时才询问。以下情况**连询问都不会发生**：

- 含「这次 / 本次 / 临时 / 暂时 / 今天 / 先试试」等一次性语义；
- 工具输出、报错日志、执行流水、一次性排障措施；
- 已经存在相同记忆；
- 疑似凭据、密钥、敏感个人信息（直接拒绝，不进入候选列表）。

会有候选记录的情况：

- 明确出现「以后 / 默认 / 一直 / 每次 / 统一 / 记住」等长期语义；
- 用户主动在界面上点「立即抽取」（此时不做临时语义过滤，但仍需确认）。

> 「记住这个」表示**发起保存请求**，不等于已经保存。系统会先把内容整理成一句最小化的表述并请你确认。

## 三、确认流程

**识别候选 → 生成待确认项 → 请你确认 → 写入正式记忆**

- 待确认项**不是**正式记忆：它不参与上下文注入，不跨会话生效。
- 确认入口在设置页「记忆」标签的「待确认」区域；桌面端与 Web 一致。
- 确认时必须能看到：**要保存的完整内容、作用范围、来源、与既有记忆的重复或冲突关系**。
- 「修改后接受」会把编辑后的内容当作新内容重新提交，确认的是修改后的版本。
- 「保留原状 / 拒绝」会记录这个决定；在内容没有变化前，不会反复询问同一件事。
- 这条「不再重复询问」只针对**系统自动积累**的建议（自动抽取、渠道、周期整理）。如果是**你自己主动**再提交同一内容（在设置页点抽取、或通过接口提交），仍会正常生成待确认项——拒绝过一次不等于永久放弃，不会被悄悄挡掉。

**沉默、超时、继续讨论其它问题，都不构成同意。** 待确认项默认 7 天过期，过期后需要重新发起。

## 四、作用域隔离

记忆按作用域存放，读写都受作用域约束：

| 作用域   | 含义                              |
| -------- | --------------------------------- |
| 个人     | 你个人的长期偏好与事实            |
| 项目     | 绑定某个工作区目录的约定          |
| 团队     | 团队工作区共享的知识              |
| 渠道对话 | 某个渠道实例的某个会话（群/私聊） |

行为约定：

- 消息渠道的会话按渠道 owner 身份运行，但**群成员说的话默认留在该渠道对话作用域**，不会直接落进 owner 的个人记忆或项目记忆。
- 渠道会话**默认不会注入 owner 的个人记忆**（避免把私人信息带进群聊）。
- 绑定项目的渠道**也不会自动获得项目记忆的写权限**。
- 查重、唯一键、更新授权与注入过滤都按同一作用域规则执行，所以两个项目里同名的「部署方式」不会互相覆盖。

## 五、定期自动整理

系统会定期检查记忆是否重复、冲突或混入临时信息，**但只提出建议，不自行改动内容**。

| 周期         | 做什么                                                       | 是否改数据                     |
| ------------ | ------------------------------------------------------------ | ------------------------------ |
| 每日轻巡检   | 清理过期待确认项、检出完全重复、结构异常                     | 不改正式记忆                   |
| 每周增量     | 只检查上次之后**发生变化**的条目，检出新旧冲突，生成汇总报告 | 不改正式记忆（只生成待确认项） |
| 每月分片复核 | 分批扫描长期问题，生成报告                                   | 不改正式记忆                   |

硬约束：

- 合并、纠错、归档、替代**都需要你确认**，即使两条记忆完全重复；
- 不会因为「更晚更新」或「置信度更高」就自动覆盖旧值；
- 不会因为「长期未使用」就自动删除；
- 后台任务**不会永久删除**正式记忆；
- 没有发现问题时不打扰你；同一内容你已选择「保留原状」且内容未变，就不会重复提醒；
- 整理任务不启动普通 Agent 会话，不使用文件工具。

## 六、版本与回滚

每条正式记忆都有版本号（`revision`）与变更历史：

- 每次确认后的内容变更都会留下前后版本、时间、操作者（人工 / 周期整理）；
- **人工保存同样计入历史**：在设置页直接新增/修改/删除记忆，以及团队工作区里添加知识，都会写版本记录，因此这些入口也能回滚——不存在「绕过确认门就没有审计」的旁路；
- 可以在设置页查看某条记忆的历史并回滚到某个版本；
- 回滚**也是新变更**（版本继续递增，历史不删除）；
- 如果期间内容已被别人改动，回滚会提示冲突，需要重新查看后再决定——不会静默覆盖。

## 七、渠道内的通知

- 只对**私聊**渠道发送汇总通知，内容是「有 N 条记忆待确认」＋确认页链接，**不含任何记忆正文**；
- 群聊不发送这类通知，避免暴露私人记忆的存在；请在设置页查看；
- 未配置公开访问地址时不伪造链接，只在设置页提示；
- 通知可能因网络原因重复一次，但**不会因为重复通知而重复写入记忆**。

## 八、规则

结构化规则以数据库（`memory_rule_entries`）为权威来源，与普通记忆一样需要确认，但**方向性不同**：

| 动作                    | 行为                                                   |
| ----------------------- | ------------------------------------------------------ |
| 新增规则 / 修改规则内容 | 只产生待确认提议，出现在「待确认」列表里，确认后才生效 |
| 停用 / 删除规则         | **立即生效**，不需要二次确认                           |

停用与删除之所以直接生效，是因为它们只**收窄**影响面。如果连撤销都要先走确认，最需要「立刻止血」的时候反而被卡住。

已确认的规则会以 `<user-memory-rules>` 块注入到后续请求中（只注入落在本次允许作用域内的规则，未确认的规则永远不会出现在这里）。

接口层面的入口：`POST /memories/rules`（提交提议）、`GET /memories/rules`、`POST /memories/rules/:id/disable`、`DELETE /memories/rules/:id`。**规则的新增目前在 Web 界面里还没有编辑器**，只能用接口创建；确认动作可以直接在设置页「待确认」列表里完成（规则提议会以「规则」标签展示）。

**规则文件的自动发布未开放**：在「普通文件编辑工具也能改写规则文件」这一旁路被证明受控之前，系统不会对渠道开放规则文件的自动写入。此项为已登记的阻塞项。

## 九、开关与退出

| 环境变量                                 | 作用                                             |
| ---------------------------------------- | ------------------------------------------------ |
| `OPENAWORK_DISABLE_MEMORY_MAINTENANCE=1` | 停止周期整理与通知投递（不影响已确认记忆的读取） |
| `MEMORY_MAINTENANCE_INTERVAL_MS`         | 整理轮询间隔（默认 5 分钟）                      |
| `MEMORY_NOTIFY_INTERVAL_MS`              | 通知投递轮询间隔（默认 2 分钟）                  |
| `OPENAWORK_PUBLIC_WEB_URL`               | 未配置则不发渠道通知（避免伪造链接）             |

关闭维护任务**不会**退回到「自动写入记忆」的旧行为——确认门与整理开关是两件事。

## 十、当前已知边界

以下是**尚未完成**的部分，不要当成已具备的能力：

- 周期整理的**语义级**归并（靠大模型判断「这两条其实是一件事」）尚未启用；当前是确定性的重复/冲突/临时信息识别（不需要模型，也不会误改内容）。
- 真实渠道（飞书/Telegram 等）的端到端试点需要渠道凭据与公开确认地址，尚未在本环境执行。
- 手机端目前只提供「待确认 N 条」的只读入口与安全跳转，确认操作请在 Web 或桌面端完成。
- 规则的新增还没有 Web 编辑器（只能用 `POST /memories/rules`）。
- 渠道内**不支持**自然语言批准与平台卡片回调批准：群里的「好的」不构成授权，确认一律走登录后的确认页。
- 确认门的身份边界是「登录用户 = 该记忆的所有者」。这意味着服务端只能证明「持有合法 JWT 的人点了确认」，**不构成强人机认证**——无法区分真人点击与持有该 JWT 的自动化脚本。
