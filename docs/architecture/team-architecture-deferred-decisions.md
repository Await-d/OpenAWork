## 0. 延后决策的两种类型

### L3 - 实施触发（落地具体功能时拍板）

特征：

- 决策的对错只能在写代码时判断
- 提前锁定无意义（缺乏上下文）
- 错了影响范围有限（单个功能）

处理方式：

- **不写进架构文档**
- 在对应 Phase 的 PR 描述里记录
- 由实施者在 review 时与 reviewer 一起决定

### L4 - 运营触发（上线后根据数据调整）

特征：

- 决策的对错必须看真实分布才能判断
- 提前锁定基本是猜测
- 错了可以在线调整（不需要发版）

处理方式：

- **不写进架构文档**
- 在运营文档（如 `runbook.md`）里维护
- 由数据指标驱动调整

## 5. 决策升级流程

### L4 → L3

当某项 L4 决策需要写进代码时（不再只是运营调整），升级为 L3，进入对应 Phase 的实施记录。

### L3 → L1

当某项 L3 决策被发现影响数据模型或通信协议时（即"决定形状"），升级为 L1，按 L1 审批流程处理。

### L1 → L1（修订）

按 L1 文档 §4 的 RFC 流程处理。
