> 本文档是**编排深度定义与判据的唯一来源**。`docs/architecture/` 下其它文档不得再定义一套深度词表或阈值，只能链接到本文。
>
> 关联方案：`.agentdocs/workflow/261029-team-编排精度与协作闭环优化方案.md`（T-02/T-14/T-15/T-16/T-17/T-18）
> 关联实现：`services/agent-gateway/src/handoff/runner/reception-router.ts`、`reception-orchestrator.ts`
> 创建时间：2026-10-31

## 1. 为什么需要深度分级

现状是「固定分层流水线」：任何进入接待层（b）且被判定为需要动手的输入，都会走
`reception → pm1（规划/规格）→ pm2（派发/双评审）→ executor/reviewer` 的完整层级。
对「改一句文案」「调一个样式」这类小改动，这会产生：

- 与改动规模不相称的 handoff 数与模型调用轮次；
- 更长的首字延迟与更高的失败面（每个层级都是一次可能的失败点）；
- 完成证据要求与实际风险不匹配时的噪声。

深度分级的目标是：**按改动面决定编排深度**，让 L1 小任务不建 PM1/PM2，同时不降低
L2/L3 的评审与证据门槛。

## 2. 深度定义

| 深度 | 语义 | 是否建 PM1/PM2 | 执行 | 完成判定 |
|---|---|---|---|---|
| **L0** | 只读/问答，不产生代码或文档变更 | 否 | 接待层直接回答（`direct` / `light`） | 回答产出即结束 |
| **L1** | 单文件/单函数的小改动，且不触碰 schema、迁移、权限、构建配置 | 否 | 复用 `runSessionInBackground` 直接执行 | 执行证据 + 可选独立复查（默认关闭） |
| **L2** | 2–5 个文件、同一模块内的功能改动 | 是 | 完整层级链路 | 双评审 + 执行凭证覆盖率 |
| **L3** | 跨包/跨模块/架构级改动，或触及 schema、迁移、权限、构建配置 | 是 | 完整层级链路 | 双评审 + 执行凭证覆盖率 + 更严格的验收场景检查 |

> 术语对齐：本文的「深度」是**编排深度**，与「角色层级 a/b/c/d/e-g」是两回事。
> 一个 L3 任务仍然是五层架构，只是进入完整分层编排；L0/L1 则是跳过中间层的浅编排。

## 3. 判据（改动面）

判据只看**改动面**，不看措辞长度或用户语气。规则优先，不确定时才让模型兜底并**要求返回深度**。

1. **L0**：无写入意图（提问、解释、查资料、只读研究）。
2. **L1**：命中单文件或单函数，且**不**涉及 `schema`、数据库迁移、权限/鉴权、构建或部署配置、公共包对外契约。
3. **L2**：涉及 2–5 个文件，且落在同一模块内。
4. **L3**：跨包/跨模块/架构级，或命中 schema、迁移、权限、构建配置中的任意一项。
5. **不确定时**：规则无法判定 → 交给模型兜底，并要求输出深度；模型输出缺失或非法时**保守取更深的深度**（L2/L3），不得静默降级为 L1。

参考用例（T-15 表驱动用例需覆盖的类别）：

| 输入类别 | 期望深度 | 说明 |
|---|---|---|
| 改一句文案 / 改一个样式 | L1 | 单文件、无契约影响 |
| 单模块功能（加接口 + 前端调用） | L2 | 多文件同模块 |
| 改迁移脚本 / 改权限逻辑 | L3 | 命中 schema/权限关键词 |
| 跨包重构 | L3 | 跨包 |
| 只读研究（解释某模块如何工作） | L0 | 无写入意图 |

## 4. 与 `reception-router` 的映射

`RouteDecision` 到深度的映射（T-14 只**新增** `orchestrationDepth` 字段，不改既有 classify 词表与判定顺序）：

| `RouteDecision` | 深度 | 说明 |
|---|---|---|
| `light` | L0 | 只读/问答 |
| `direct` | L0 | 前台直答 |
| `clarify` | — | 尚未成任务，需继续澄清后再定深度 |
| `grill` | — | 先澄清拷问，确认后再定深度 |
| `resume` | 继承 | 继承被恢复任务已有的深度，不重算 |
| `orchestrate` | L2 / L3 | 由 §3 判据细分 |

> 关键约束：深度**只增字段、不改判定**。`reception-router` 现有判定用例必须全部保持通过；
> 深度是判定的补充产物，不是新的路由分支。

## 5. 各深度的行为差异

- **L0**：不初始化团队产物、不创建 handoff，直接由接待层回答。
- **L1**：不创建 PM1/PM2；复用 `runSessionInBackground` 执行；完成后可选生成 1 条 reviewer 型
  handoff 做独立检查（**默认关闭**，可按工作区配置开启）。深度必须在接待层首条消息可见。
- **L2/L3**：与改前行为一致，唯一差异是「精简门禁」——L2 可省略与规模不相称的仪式性步骤，
  但**双评审与执行凭证核验仍然生效**。

## 6. 可观测与可覆盖

- handoff 记录需携带 `depth`，任务面板可查看本次深度与判据来源（规则/模型）。
- 接待层首条规划消息标注「本次按 L{n} 执行」，并提供「升级为完整流程」入口；
  用户强制升级后**从当前进度续接**，不重跑已完成的产物（例如不重新生成 spec）。
- 深度降级（判据不确定、模型输出非法）需记录为可观测事件，不得静默发生。

## 7. 非目标

- 不改变五层架构与跨层受控通道（L1.4 约束不变）。
- 不引入共享目录隔离或 worktree 级并行（属架构级变更，需单独方案）。
- 不用深度分级替代完成证据核验：任何深度都不接受「自报完成」。
