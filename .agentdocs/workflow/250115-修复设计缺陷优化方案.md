## 任务概述

基于 DESIGN_DEFECTS.md 分析，OpenAWork 项目存在 11 个关键设计缺陷，涵盖代码模块化、错误处理、流式架构、权限校验等维度。本方案将这些缺陷分为三个阶段修复，制定具体实施步骤、验证策略和时间估算。

## 修复方案设计

### 第一阶段：P0 - ChatPage 超大文件拆分

#### 目标
将 3717 行的 ChatPage.tsx 按职责边界拆分为 6 个独立组件/hook，每个 <500 行。

#### 具体拆分方案

**1. ChatPage.tsx 保留核心（>300 行）**
- 主应用路由逻辑
- 页面布局（左侧树、中间聊天、右侧面板）
- Session 选择与切换
- 关键 hook 组装

**2. hooks/use-chat-page-core-state.ts（新建，~200 行）**
- `useChatPageCoreState` hook
- 会话创建、恢复、删除逻辑
- 本地状态初始化
- 当前内容：ChatPage.tsx 第 150-450 行

**3. hooks/use-chat-composer-actions.ts（新建，~150 行）**
- 发送、停止、队列、优化相关 callback
- 消息提交、流式控制
- 当前内容：ChatPage.tsx 中分散的 `onSubmit`, `onStop`, `onQueue` 等

**4. hooks/use-chat-shortcuts.ts（新建，~100 行）**
- 快捷键处理（Enter/Cmd+Enter/Cmd+Shift+F 等）
- 目前由 `useChatComposerShortcuts` 单独负责

**5. hooks/use-chat-search-integration.ts（新建，~80 行）**
- 搜索面板状态与事件
- 搜索结果高亮
- 当前内容：search-overlay 集成逻辑

**6. hooks/use-chat-recovery-polling.ts（现有，已独立）**
- 保持现有

### 第二阶段：P1 - 流式和错误处理修复

#### 1. stream.ts 分层架构重构

##### 目标
将 >1000 行的单一 handler 拆分成 5 个专责模块，建立清晰的数据流。

##### 拆分方案

**模块设计：**
```
stream-handler.ts (核心编排，~200 行)
├── stream-auth.ts (权限检查，~100 行)
├── stream-agent-executor.ts (Agent FSM + 工具调用，~300 行)
├── stream-persistence.ts (消息 + 事件 + diff 存储，~200 行)
├── stream-sse-encoder.ts (SSE 协议编码，~150 行)
└── stream-error-handler.ts (统一错误处理与降级，~150 行)
```

##### 具体步骤

**T-08：建立测试用例**（1 天）
- 为 stream.ts 增加集成测试覆盖：
  - 成功流式路径

  - 网络中断路径
  - 消息持久化路径
- 运行测试确保基线通过

**T-09：提取 stream-auth.ts**（1 天）

- 测试持久化一致性

**T-11：提取 stream-sse-encoder.ts**（0.5 天）

**T-12：提取 stream-error-handler.ts**（1 天）

#### 2. 错误处理统一化

##### 目标

##### 具体步骤

- 定义 `GatewayError` 基类（若不存在）
- 定义错误分类枚举：
  ```typescript
  enum ErrorCategory {
    AuthFailure = 'auth_failure',
    ParseFailure = 'parse_failure',
    PermissionDenied = 'permission_denied',
    ToolExecutionFailed = 'tool_execution_failed',
    NetworkError = 'network_error',
    UnexpectedError = 'unexpected_error',
  ```

**T-16：扫描并记录所有空 catch**（0.5 天）

**T-17：修复权限校验中的 catch**（1 day）
- `permission-contract.ts` 中 10 个空 catch
- 每个添加 `logger.warn()`，记录错误类别
- 示例：

- 单元测试验证日志输出

**T-18：修复浏览器下载中的 catch**（1 day）
- `browser-live/*.ts` 中 8 个空 catch
- 部分是预期的（如 CLI 不存在），需添加 debug 日志
- 部分是异常（如下载失败），需 warn 日志
- 测试下载失败场景

**T-19：修复权限衍生中的 catch**（1 day）
- `tool-permission-derivers.ts` 中的 catch
- 每处记录：尝试什么操作、为何失败、采用了什么降级
- 示例：
  ```typescript

      'Failed to derive permission, falling back to info-only');
  }
  ```

#### 3. 定时任务 API 稳定化

##### 目标
建立明确的定时任务接口契约，减少跨模块改动。

##### 问题根源
最近 5 次提交都涉及定时任务，表明 API 边界不清晰。涉及文件：
- gateway 中的路由、权限、执行、结果投递
- agent-core 中的调度逻辑（如有）
- web 中的页面刷新与 UI 状态

##### API 稳定化方案

**T-20：定义 ScheduledTask 契约**（1 day）
- 建立 `packages/shared/src/scheduled-task-contract.ts`
- 定义接口（最终态）：
  ```typescript
  export interface ScheduledTaskDefinition {
    id: string;
    name: string;
    cronExpression: string;
    timezone: string;
    agentConfig: AgentConfig;  // 关键参数
    createdBy: string;
    createdAt: Date;
  }
  
  export interface ScheduledTaskExecution {
    id: string;
    taskId: string;
    startedAt: Date;
    completedAt?: Date;
    status: 'pending' | 'running' | 'success' | 'failed';
    result?: RunEvent[];
    errorMessage?: string;
  }
  ```
- 用 Zod 定义 schema
- 不在 gateway、agent-core、web 中各自重复定义

**T-21：网关端 API 规范化**（1 day）
- 创建专属路由文件 `services/agent-gateway/src/routes/scheduled-tasks.ts`
- 路由设计：
  - `POST /scheduled-tasks` — 创建（需权限检查）
  - `PUT /scheduled-tasks/:id` — 更新
  - `DELETE /scheduled-tasks/:id` — 删除
  - `GET /scheduled-tasks/:id/executions` — 查看执行历史
  - `POST /scheduled-tasks/:id/trigger` — 手动触发
- 所有路由共用权限检查、结果投递、审计日志逻辑
- 与 `/stream` 无耦合（分离关切）

**T-22：定时任务触发机制独立**（1 day）
- 创建 `services/agent-gateway/src/scheduled-tasks/trigger-engine.ts`
- 职责：定时检查、触发、记录执行
- 与 stream.ts 解耦（trigger-engine 调用 stream，不混在一起）

**T-23：UI 同步规范**（0.5 day）
- 在 `apps/web` 中使用 EventSource 订阅执行结果
- 路由：`GET /scheduled-tasks/:id/stream` 返回 SSE
- 页面自动刷新逻辑封装到 hook（如 `useScheduledTaskStream`）
- 不在页面组件中硬编码

**T-24：测试与文档**（1 day）
- 为新 API 写集成测试
- 更新 API 文档
- 记录契约变更到 `.agentdocs/index.md`

#### 验证策略
- [ ] 定时任务 API 在 `@openAwork/shared` 中单一定义
- [ ] gateway、web、core 都导入该定义（无重复）
- [ ] 新路由 `/scheduled-tasks/*` 完全独立于 `/stream`
- [ ] 集成测试覆盖：创建、更新、删除、手动触发、自动触发、执行历史查询
- [ ] 最近 5 次定时任务相关提交可以在新 API 下轻松实现（不需额外改动）
