#### 1. 持久化事务一致性（T-25 ~ T-27）

##### 问题分析
当前持久化操作分散在多个模块，无事务保证：
- `stream-persistence.ts` 中消息、事件、文件 diff 多次 I/O
- 若中途崩溃，可能消息已保存但事件未记录，导致状态不一致
- 权限变更、定时任务执行也有类似问题

##### 目标
建立原子操作语义，确保"全成功或全失败"。

##### 具体方案

**T-25：设计事务抽象层（1 天）**
- 创建 `services/agent-gateway/src/infra/transaction.ts`
- 定义事务接口（不依赖具体数据库，支持 SQLite/Postgres）：
  ```typescript
  export interface Transaction {
    run<T>(fn: (trx: Transaction) => Promise<T>): Promise<T>;
    saveMessage(msg: Message): Promise<void>;
    saveEvent(event: StreamEvent): Promise<void>;
    saveFileDiff(diff: FileDiff): Promise<void>;
    savePermissionAudit(audit: PermissionAudit): Promise<void>;
    commit(): Promise<void>;
    rollback(): Promise<void>;
  }
  
  export interface TransactionManager {
    begin(): Promise<Transaction>;
  }
  ```
- 先用内存实现（for 测试），再切换到 SQLite
- 提交文档：`docs/transaction-design.md`

**T-26：改造 stream-persistence.ts 使用事务（1 天）**
- 将 `persistStreamSnapshot()` 改为接收 `Transaction` 参数
- 示例：
  ```typescript
  export async function persistStreamSnapshot(
    trx: Transaction,
    messages: Message[],
    events: StreamEvent[],
    diffs: FileDiff[],
  ) {
    for (const msg of messages) {
      await trx.saveMessage(msg);
    }
    for (const event of events) {
      await trx.saveEvent(event);

    // ...

  ```

**T-33：改造 trigger-engine 支持队列与优先级（1 day）**
- 改进 `services/agent-gateway/src/scheduled-tasks/trigger-engine.ts`：
  ```typescript
  export class TriggerEngine {
    private queue: PriorityQueue<ScheduledTaskExecution>;
    private concurrencyLimit = 3;  // 从 env 读取
    private activeExecutions = new Map<string, Promise<void>>();
    
    async trigger(taskDef: ScheduledTaskDefinition) {
      const execution: ScheduledTaskExecution = {
        id: generateId(),
        taskId: taskDef.id,
        status: 'pending',
        priority: taskDef.priority,
      };
      
      this.queue.enqueue(execution);
      this.processPending();
    }
    
    private async processPending() {
      while (this.activeExecutions.size < this.concurrencyLimit) {
        const execution = this.queue.dequeue();
        if (!execution) break;
        
        const promise = this.executeTask(execution)
          .finally(() => this.activeExecutions.delete(execution.id));
        
        this.activeExecutions.set(execution.id, promise);
      }
    }
  }
  ```
- 提供 API 查看队列状态：`GET /scheduled-tasks/queue/status`
  ```json
  {
    "active": [{ "id": "exe-123", "taskId": "task-1", "startedAt": "..." }],
    "pending": [{ "id": "exe-124", "taskId": "task-2", "priority": 2 }]
  }
  ```
- 单元测试：
  - 高优先级任务插队执行
  - 并发限制生效
  - 不同优先级的执行顺序正确

## 回滚与应急预案

### 分阶段回滚策略

#### P0 阶段回滚

**场景 1：ChatPage 拆分后出现功能缺陷**
- 时间窗口：T-07 提交 PR 后 24h 内发现 → 可直接回滚
- 时间窗口：已合并 >3 天 → 记录 bug，下周用 bug fix commit 修复

**回滚指令**
```bash
# 若 PR 尚未合并，关闭 PR
gh pr close <pr-number>

# 若已合并但未发布，使用 revert
git revert <commit-sha>
git push -u origin revert-chatpage

# 若已发布到生产，需要 hotfix
git checkout -b hotfix/chatpage-fix main
# 进行修复
git push -u origin hotfix/chatpage-fix
# 提交 PR 并加急合并
```

**预防措施**
- ChatPage 拆分的每个 hook 都有独立的单元测试
- 集成测试覆盖完整页面流程
- 合并前进行 30min+ 的手工冒烟测试

#### P1 阶段回滚

**场景 1：stream.ts 分层导致流式中断**
- 症状：客户端收到 SSE 断流、消息丢失等
- 诊断：检查 stream-error-handler.ts 是否正确分类错误
- 回滚方案：
  ```bash
  # 若未发布，直接 revert 整个分层提交
  git revert <commit-sha>^..<commit-sha>  # revert 5 个提交
  
  # 若已发布，需要 hotfix：快速修复错误处理，不回滚整个分层
  git checkout -b hotfix/stream-error-classify main
  # 改正 stream-error-handler.ts 中的错误分类
  ```

**场景 2：错误处理改造导致日志风暴**
- 症状：日志量激增 100 倍，磁盘满
- 诊断：检查是否有无限循环的 logger 调用
- 快速缓解：
  ```bash
  # 临时降低日志级别
  export LOG_LEVEL=error
  # 重启网关
  ```
- 永久修复：修复 logger 调用，重新部署

**预防措施**
- stream 分层的 5 个模块各有独立的单元测试
- 集成测试覆盖：权限拒绝、工具失败、网络中断等异常路径
- 部署前运行压力测试，观察日志量

**场景 3：定时任务 API 改版破坏兼容性**
- 症状：旧客户端无法创建定时任务
- 回滚方案：
  ```bash
  # 使用版本号区分 API
  # 旧版本客户端调用 POST /v1/scheduled-tasks
  # 新版本调用 POST /v2/scheduled-tasks
  
  # 暂时同时支持两个版本
  git checkout -b feature/scheduled-tasks-v2-compat main
  # 在网关中实现 v1 → v2 的转换层
  ```

#### P2 阶段回滚

**场景 1：事务系统导致数据库死锁**
- 症状：请求超时、事务 rollback
- 快速缓解：禁用事务（改回原来的实现），保证可用性
- 永久修复：分析死锁原因，调整事务边界

**场景 2：权限决策中心拒绝了合法请求**
- 症状：用户反馈无法执行某些操作
- 回滚方案：
  ```bash
  # 快速开关：环境变量禁用新权限检查
  export PERMISSION_CHECK_LEGACY=true
  # 网关会转向旧的权限检查逻辑
  ```
- 永久修复：调整权限规则，重新审批

### 全局回滚计划

**回滚决策树**
```
发现问题
  ├─ 影响 <1% 用户 → 记录 bug，下周修复
  ├─ 影响 1-10% 用户 → 立即 hotfix（不回滚）
  └─ 影响 >10% 用户或系统不可用 → 回滚

回滚执行
  ├─ 若 <1 小时发现 → 回滚到上一个稳定版本
  ├─ 若 1-4 小时发现 → 分析影响范围，评估回滚代价
  └─ 若 >4 小时 → 通常不回滚，改为 hotfix
```

**回滚检查清单**
- [ ] 确认症状确实由本次部署引起（不是网络问题）
- [ ] 获得项目主管和 CTO 口头授权
- [ ] 通知 DevOps 团队准备回滚
- [ ] 记录回滚理由到 `.agentdocs/incidents/`
- [ ] 回滚后验证系统恢复正常
- [ ] 召开事后会（Postmortem），记录根本原因

## 常见问题

**Q：如果某个 task 遇到意外困难，应该怎么处理？**  
A：立即通知项目主管，可以选择：
1. 延期该 task 1-2 天（调整后续 task 的日期）
2. 寻求其他成员支持（code pairing）
3. 临时跳过该 task，先完成后续 task（需评估影响）

**Q：如果两个 PR 之间有冲突，应该怎么处理？**  
A：遵循优先级：P0 > P1 > P2。先合并优先级高的，再 rebase 优先级低的。

**Q：如果测试覆盖率无法达到 80%，应该怎么处理？**  
A：记录原因（如"某 legacy 代码难以单测"），向 QA lead 说明，改为加强集成测试和 E2E 测试。

**Q：新增的模块/hook 应该放在哪里？**  
A：遵循 CLAUDE.md 的拆分规则：
- 页面子区域 → `src/components/<PageName>/`
- 跨页面通用 → `src/components/` 或 `packages/shared-ui/`
- 纯展示组件 → `packages/shared-ui/src/`

**Q：如何验证改动没有功能回归？**  
A：
1. 运行现有的单元测试：`bun run test`
2. 运行现有的 E2E 测试（Playwright）
3. 手工验证关键用户流程（30min+）
4. 对比拆分前后的功能行为（无差异）
