## 终止决策（2026-09-21）

**决策**：不做「提供商侧文件引用（provider file_id / Files API）」通路。

**理由（用户判断）**：本平台的上游**不一定是官方端点**，大量用户走第三方中转 / 自建兼容端点，
这些端点**不保证实现 Files API**。因此把「引用通路」做进产品会在中转场景下不可靠甚至直接失败，
不适合本平台。

## Task Overview（原始方案，已终止）

在现有「一律 base64 内联」之外，为 OpenAWork 补齐多模态媒体的**引用通路**：按官方协议以
OpenAI `input_image.file_id` / Anthropic `source.type='file'`（Files API）发送图片，使
① 长多轮对话不再每轮重传图片字节；② 超过内联上限的图片可用而非必然失败。

官方协议核对结论（本轮已完成调研，来源见「参考来源」）：

- **OpenAI**：内联(data URL) / 公网 URL / `file_id` 三者并列；**Chat Completions 的图片没有 `file_id`**，仅 Responses 有。
- **Anthropic**：`base64` / `url` / `file` 三者并列，官方**明确推荐**大文件与长多轮走 Files API；Files API 已转正，**无需 beta header**。
- **Gemini / Bedrock**：协议层亦有引用路径（`fileData.fileUri` / `s3Location`），但**网关当前协议派发面不含它们**（见 Current Analysis），本轮排除。

## Current Analysis

### 已核实事实

1. **网关可达协议只有 3 个**：`routes/upstream-protocol.ts:1` 的
   `UpstreamProtocol = 'chat_completions' | 'responses' | 'anthropic_messages'`；
   `packages/agent-core/src/provider/catalog.ts:36` 的 `CatalogUpstreamProtocol` 同集合。
   **决定性证据**：网关唯一的模型构造点 `v2-runtime/upstream/native-model.ts:39-59` 只产出
   `Providers.Anthropic` / `Providers.OpenAI.responses` / `Providers.OpenAI.chat` / `Providers.OpenAICompatible`
   四种形态，**没有 Gemini 或 Bedrock 分支** → `protocols/gemini.ts`、`protocols/bedrock-converse.ts` 不可达
   → **Gemini `fileData` / Bedrock `s3Location` 引用路径今日不可用**，本轮不纳入。
   （附带记账：`v2-runtime/upstream/provider-options.ts` 存在 Google thinking 配置，疑为未接线前预留，另行核实，不阻塞本方案。）

2. **协议层只接受内联 base64**：`protocols/shared.ts` 的 `validateMedia` 明确拒绝非 base64（含 URL），
   并有 `IMAGE_MIMES` / `MAX_MEDIA_ENCODED_BYTES=28MiB` / `MAX_MEDIA_DECODED_BYTES=20MiB` 三处硬约束；
   `schema/messages.ts:45` 的 `MediaPart` 只有 `{type:'media', mediaType, data, filename?}`。

3. **schema 里已有 `fileId` 字段，但全链路无人生产/解析**（死字段）：
   入参 `routes/stream.ts:533-542`；消息 part `message-v2-schema.ts:142`、`message-v2-adapter.ts:115/144/253/649`；
   统一模型消息 `message-to-model-messages.ts:604-633`（`collectAttachmentImages`）与 `662-670`（`buildUserInput`）。
   → 复用该字段承载「网关生成的 provider 文件 id」是**加法扩展**，客户端协议无需改动。

4. **协议适配器用 `if (part.type === …)` 顺序链，无 `assertNever`**：新增 `ContentPart` 变体**不会**触发编译错误。
   但 `shared.ts:355-368` 提供 `supportsContent()` / `unsupportedContent()`「白名单 + 明确报错」机制。
   **[T-02 已验证] 6/6 适配器均有该兜底**（`openai-chat.ts:247`、`openai-responses.ts:349`、
   `anthropic-messages.ts:487`、`gemini.ts:228`、`bedrock-converse.ts:342`；`openai-compatible-chat.ts:19`
   复用 `OpenAIChat.protocol` 继承）→ 新变体**不会被静默丢弃**，会被明确拒绝；
   接入方式即把 `'media-ref'` 加进对应适配器的白名单数组。

5. `validateMedia` 的上限常量**未从包根导出**（`protocols/index.ts` 只导出命名空间），
   上一轮修 `look_at` 时只能按名镜像常量 → 本轮先补命名导出，消除手工同步。

### 约束

- 仓库记忆：**跨前后端改造优先用「可选字段加法扩展」，不做破坏性改字段**（`index.md` 2026-09-15）。
- **安全**：Anthropic 官方明确「上传文件对整个 workspace 可见、不按用户隔离」→ **绝不接受客户端传入的 `file_id`**，
  只能由网关自行上传产生；表必须带 `userId` 归属，默认不跨用户复用。
- 网关禁止在 `db.ts` 之外加同步阻塞代码；上传必须异步。
- 每阶段改动 ≤3 文件（Gate 2）。

## Solution Design

### D1 协议层：新增 `MediaRefPart`（加法扩展，`MediaPart` 零改动）

```ts
// packages/opencode-llm/src/schema/messages.ts
export const MediaRefPart = Schema.Struct({
  type: Schema.Literal('media-ref'),
  mediaType: Schema.String,
  ref: Schema.Union([
    Schema.Struct({ kind: Schema.Literal('provider-file'), fileId: Schema.String }),
    Schema.Struct({ kind: Schema.Literal('url'), url: Schema.String }),
  ]),
  filename: Schema.optional(Schema.String),
});
```

加入 `ContentPart` union（`Schema.toTaggedUnion('type')`）。内联 `MediaPart` 完全不动 → 现有路径零回归。

### D2 能力声明集中在协议层

`shared.ts` 新增 `MediaRefCapability = { providerFile: boolean; url: boolean }`，各协议导出常量：

| 协议 | providerFile | url | 依据 |
| --- | --- | --- | --- |
| `OpenAIChat` | ❌ | ✅ | 官方：Chat 图片 part 无 `file_id` |
| `OpenAIResponses` | ✅ | ✅ | 官方：`input_image.file_id` + `image_url` |
| `AnthropicMessages` | ✅ | ✅ | 官方：`source.type=file` + `url` |
| gemini / bedrock / compatible | ❌ | ❌ | 网关未接线；lowering 明确拒绝 |

### D3 网关：provider 文件生命周期管理器（新目录 `src/provider-files/`）

- `provider-file-store.ts`：`ensureProviderFile(...) → fileId`
  - 缓存键 `(userId, providerType, apiBaseUrl, sha256(bytes))` → 内容哈希幂等，同一 artifact 跨会话复用
  - SQLite 表 `provider_files(id, user_id, provider_type, api_base_url, content_hash, provider_file_id, mime_type, expires_at, created_at)`，唯一索引含 `user_id`
- `openai-file-uploader.ts` / `anthropic-file-uploader.ts`：`POST /v1/files`
- 过期 / 上游 404 → 标记失效并**重新上传**；重建失败且 ≤ 内联上限 → **降级内联**

### D4 传输策略 SSOT（纯函数，可单测）

`src/media/media-transport-policy.ts`:

```ts
decideMediaTransport({ protocol, capability, byteLength, mimeType, reuseCount })
  → 'inline' | 'provider-file' | 'url'
```

规则：≤ 协议内联上限 → `inline`（保持现状）；超上限且 `capability.providerFile` → `provider-file`；
超上限且无能力 → 抛**明确错误**（不再交给上游抛难懂错误）；同一 artifact 本会话复用 ≥2 次 → 倾向 `provider-file`。

### D5 投影接线（**P2 期间已修正**：凭据只在 upstream 回合可得）

> **修正依据**：`session/stream-session-title.ts` 的 `resolveInputImageContent` 只解析产物字节，
> **拿不到 provider 凭据**；网关唯一同时具备 `providerType / upstreamProtocol / apiKey / apiBaseUrl`
> 的位置是 `routes/stream-model-round.ts:1561` 的 `buildNativeModel({ … input.route })`
> （`ModelRouteConfig` 携带 `apiKey`）。因此**上传只能发生在该处**，而不是持久化时。

1. `stream-model-round.ts` 在 `buildNativeModel` 之前，按 `MediaRefCapability`（由 `upstreamProtocol` 映射）
   + 内联上限 + 会话内复用次数，用 `decideMediaTransport` 挑出应走引用的 artifact；
2. 逐个调 `ensureProviderFile(...)` 上传/命中缓存，得到 `artifactId → providerFileId` 映射；
3. 把该映射交给 `message-to-model-messages.ts` 的「统一消息 → `LLMRequest`」转换，命中项产出
   `MediaRefPart`（T-05 已支持降级），其余维持 `MediaPart` 内联。

`routes/stream.ts` 的 schema **不改**（`fileId` 字段已存在），`stream-session-title.ts` 保持现状。

### D6 明确排除本轮范围

- **文档（非图片）通路**（Anthropic `document` block / OpenAI `input_file`）：属一整类新 content part + 前端渲染，**单独成方案**。
- **Gemini / Bedrock 引用路径**：先决条件是网关接线其协议派发（独立任务）。
- **S3 上传器**：Bedrock 需用户自备桶，属部署配置，不在本轮。

## opencode 对照结论（2026-09-21 调研）

调研对象：`temp/opencode`（`github-v1.2.25-2014-g88c6c7abc7`）。**结论：opencode 与「不做引用通路」的判断完全一致。**

| 议题 | opencode 的做法 | 证据 |
| --- | --- | --- |
| 提供商文件上传 | **完全不存在**：无 `/v1/files`、无 multipart、无 `file_id` 生产 | `packages/llm` 内 0 命中；`file_id`/`input_file` 仅存在于 vendored GitHub Copilot provider 的 **passthrough** 类型中，opencode 自身数据流永不触发 |
| 图片上行 | **100% 内联 base64**：Chat `image_url.url=data:`、Responses `input_image.image_url=data:`、Anthropic `source.type=base64`、Gemini `inlineData`、Bedrock `image.source.bytes` | `packages/llm/src/protocols/*` |
| 公网 URL 图片 | **不支持**（`validateMedia` 拒非 base64；session 入口 switch 只处理 `data:`/`file:`）→ **刻意规避 SSRF 面**，无 URL 抓取即无白名单责任 | `packages/llm/src/protocols/shared.ts`、`packages/opencode/src/session/prompt.ts` |
| 文本文件 | 经 `read` 工具**内联正文为文本**，上限 2000 行 / 50KB / 单行 2000 字符 | `packages/opencode/src/tool/read.ts`、`session/prompt.ts` |
| PDF | **不抽文本**，整份 base64 交给原生支持 `pdf` 模态的模型；不支持则降级为文本提示 | `tool/read.ts`、`provider/transform.ts` `unsupportedParts` |
| docx/xlsx/pptx | **明确拒绝**（binary），内容不到模型 | `tool/read.ts`（`Cannot read binary file`） |
| 能力声明 | `modalities.input` 含 `image`/`pdf`；自定义/openai-compatible provider **默认 image/pdf=false、text=true**；用户可在 config 覆盖 | `packages/core/src/models-dev.ts`、`packages/opencode/src/provider/provider.ts` |
| 不支持的降级 | 替换为**一段让模型转告用户的错误文本**（不丢弃、不硬失败） | `provider/transform.ts:409-445` |
| 运行时探测 | 无「发探针图片」机制；仅 Copilot / Modal 用 `GET /models` 做能力发现 | `plugin/github-copilot/models.ts`、`plugin/modal/models.ts` |

**对本平台的启示（后续可另立方案）**：真正差距不在图片引用，而在**非图片文件**——
① 文本文件应内联正文（带上限）而非只发文件名；② PDF 应原样 base64 给支持 pdf 模态的上游、不支持则给模型明确提示；
③ docx/xlsx 应明确拒绝并告知，而不是让模型误以为能看到；④ 能力位建议引入 `input.image` / `input.pdf`（默认 false）+ 请求前降级。
