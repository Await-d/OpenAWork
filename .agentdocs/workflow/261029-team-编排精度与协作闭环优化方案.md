# Team 编排精度与协作闭环优化方案

## Task Overview

把当前 Team 从「固定分层流水线」改造成「按任务规模分级、消息可靠、完成可信」的协作编排：

1. **小任务不再背全套规划成本**（单文件改文案不产生 PM1/PM2 handoff）。
2. **复杂任务不再静默丢任务、错依赖、假并发**。
3. **跨会话消息从「落库」升级为「可被 Agent 真正消费并唤醒」**。
4. **完成声明区分「自报完成」与「有证据完成」**。

本方案只做正确性与精度收口，**不新增角色层、不新增常驻进程、不做全量成员邮箱**。

## Solution Design

### 设计原则

1. **正确性优先于能力扩张**：先做到「不丢任务、不丢消息、不假完成」，再谈横向协作增强。
2. **单一真相源**：任务依赖、消息投递、完成证据各自只有一个权威载体，禁止多路并行推断。
3. **分级编排**：用 `orchestrationDepth`（L0–L3）表达编排深度，替代「direct/light ↔ orchestrate」二元跳变。
4. **降级必须可见**：任何截断、跳过、降级、未验证，都必须在会话内对用户可见，不得静默。

### 编排深度分级（核心设计）

| 深度 | 触发 | 执行形态 | 是否建 PM1/PM2 |
|---|---|---|---|
| L0 direct | 问候、致谢、状态查询 | reception 直接回答 | 否 |
| L1 fast-lane | 单文件/单函数小改、文案、样式微调、明确一处修复 | reception 直接执行 → 可选 1 次独立 review | 否 |
| L2 standard | 2–5 文件、单模块、边界清楚 | PM1 规划 → PM2 精简派发（跳 Grill / 架构门禁） | 是（精简） |
| L3 full | 跨包/跨模块、schema·迁移·权限·构建配置、架构级 | 现行全链（规格三产物 + 双评审） | 是（全量） |

**判据来源**：路径/文件数、模块数、是否触及 schema 迁移与权限、是否跨包、是否改动构建配置；规则先行，LLM 兜底。**不按关键词判断规模**（现有 `EXPLICIT_ORCHESTRATE_PATTERNS` 保留为「必须执行」信号，不再作为深度信号）。

### 关键决策与备选

- **D-1 小改动入口**：保留统一聊天入口，深度由路由决定；不新增「快速模式」按钮（避免用户多一层选择）。用户可在首条消息后强制升级深度。
- **D-2 超限计划**：先做**显式失败 + 未派发清单**（无新状态机，成本最低）；分批续派列为后续独立项（需跨 handoff 会话状态，风险高）。
- **D-3 完成证据**：不新增 handoff 终态，改为在 `checklist[]` 增加 `verified: boolean`；`status=completed` 但无 verified 项时，Quality Review 必须以 `unverified` 记入报告并降低总体结论，而不是直接 pass。
- **D-4 消息通道**：`POST /team/messages` 保留为**审计留言板**并在 API 文档标注「不投递给 Agent」；Agent 间通信统一走 inbound + outbox + 租约，不引入第二套邮箱。
- **D-5 附件**：扩展 inbound `user_input` payload 支持 `inputParts`（与 stream 对齐），而非绕道重传文件。
- **D-6 文件隔离**：本期**不做**成员独立 worktree；改为派发前做 ownedPaths 冲突检测并在派发卡片与 PM2 消息中提示「共享目录」。worktree 另立项。

### 范围边界（明确不做）

- 不新增角色层（tester/architect 仍映射到 executor/reviewer）。
- 不重写 `packages/multi-agent`（其 `MessageBusImpl` 未接入生产，本期不动）。
- 不做成员全量邮箱、不做消息优先级抢占（业务消息仍在边界消费）。
- 不引入分布式锁/真实 Redis（沿用进程内 + SQLite 租约）。
