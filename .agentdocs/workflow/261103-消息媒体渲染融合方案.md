# 261103-消息媒体渲染融合方案

## Task Overview

把「聊天消息里的媒体渲染」从当前**四套互不相通的实现**收敛为一套融合规则，并按风险分三期落地：

- **P1-A 图片自适应拼贴**（纯前端，零跨包依赖）
- **P1-B 消息内文件卡片**（补「非图片附件零渲染」缺口，**含数据路线决策，是本期唯一的架构分叉点**）
- **P2 视频 / 音频收敛为统一媒体卡片**
- **P3 共享增强灯箱**（缩略图条 + 键盘提示 + 加载/失败态）

设计原型已交付并获用户确认方向：`docs/media-render-demo/`（`index.html` / `styles.css` / `app.js`，纯静态可开）。用户 2026-11-03 明确「三个方案都喜欢」，故本方案采用**融合路线**而非三选一：图片走拼贴、非图片走卡片、全部共享同一灯箱。

### 2. ⚠️ 关键发现：文件卡片的数据链路**完全不存在**（三层全断）

动手前已用独立探索核实（`MessageContent` 类型、上传组装、网关落库读回、产物关联四路），结论如下：

1. **类型层缺失**：`packages/shared/src/message-schema.ts:239-247` 的 `MessageContent` 只有 `TextContent` / `InputImageContent` / `InputAudioContent` / `InputVideoContent` / `ReasoningContent` / `ToolCallContent` / `ToolResultContent` / `ModifiedFilesSummaryContent` —— **没有** `input_file` / `file` / `document` 成员（确定不存在）。
   - 旁证：V2 内部 `MessagePart` 其实**有** `FilePart`（`services/agent-gateway/src/message/message-v2-schema.ts:139-161`，带 `mime`/`filename`/`url`/`inputType`），但读回流 V1 时被收窄 —— `v2ToV1Message` 只还原 `inputType === 'input_image'`，其余 file part **被丢弃**（`services/agent-gateway/src/message/message-v2-adapter.ts:280-293`）。
2. **前端组装层压平**：`apps/web/src/pages/chat-page/conversation/composer/prepare-standard-chat-send-input.ts:48-69` —— 只有 `type === 'image'` 变成结构化 `input_image` part；**PDF / 音频 / 视频 / 代码等一律压平成文本行**（`.filter(a => a.type !== 'image')`）。
3. **网关落库丢弃**：`services/agent-gateway/src/routes/stream.ts:650-668`（`buildStreamUserContent`）、`session/stream-session-title.ts:41-52`、`message-v2-adapter.ts:773-793`（写入端）**都只认 `input_image`**。
4. **产物↔消息无关联**：`Message` / 前端 `ChatMessage` 均**无** `artifacts` / `artifactIds` 字段；`ArtifactRecord` 无 `messageId` 列（`packages/artifacts/src/artifact-content.ts:33-45`）；`metadata.originMessageId` **已声明但全仓零写入**（`:26-31`，唯一命中处）；`listForSession` / `session-artifacts-flight.ts:35-43` 入参**不接受** `messageId`。

## Solution Design

### 融合规则（实现时只需记住这一条）

> **图片 → 拼贴；视频 / 音频 / 文件 → 卡片；全部共享同一个增强灯箱。**

理由：图片本身就是内容，套卡片壳是多余层级；视频 / 音频 / 文件需要元信息（尺寸、时长、大小）与控制（播放、下载、预览），必须套壳。这条规则同时化解了「方案 A 与方案 B 在图片上冲突」的问题。

补充硬约束（延续既有约定）：

- 浮层配色一律 `--bg-elevated` + `--fg-strong` + `--border-emphasis`，**禁止** `--fg-on-accent`（历史 bug：暗色主题下近黑，压在深色遮罩上不可见，已由 `ChatPageSections.css:1-13` 与 `image-lightbox.css:9-13` 注释固化，且被测试断言覆盖）。
- 样式不硬编码色值（现有测试用正则禁 `#hex` 与 `rgba(`），媒体区新增样式必须走 token。
- 图片布局规则（数量 → 布局）以 `docs/media-render-demo/index.html` 的 D2 表为准，实现时写成纯函数 + 表格驱动。

## 附录 · Gate 0 原始选项（已按上表拍板，留档）

### D-1 文件卡片的数据路线（**P1-B 的唯一阻塞项**）

现状是三层全断（见 Current Analysis §2），因此必须先选一条路：

- **路线 1 · 结构化 file part 全链路（最正，最重）**
  给 `packages/shared/src/message-schema.ts` 的 `MessageContent` 增加 `input_file` 成员 → 前端组装层产出该 part → 网关 `buildStreamUserContent` / `stream-session-title` / `message-v2-adapter` 写入与读回双向支持 → 前端渲染卡片。
  - 优点：架构正确，模型也能拿到结构化文件信息（当前只有一行文本）。
  - 代价：跨 3 包（shared / gateway / web），需处理 V1↔V2 兼容、历史消息读回、渠道入站消息（渠道侧是否会产生 file part）；改动面最大，回归风险最高。
- **路线 2 · `originMessageId` 接线（中等，有时序陷阱）**
  写入 `ArtifactRecord.metadata.originMessageId`（该字段已声明、零写入）→ 网关读接口支持按 `messageId` 过滤 → 前端按消息取产物渲染卡片。
  - 优点：复用已有产物表，不新增 part 类型；对「助手产出的文件」同样适用（可覆盖生成物落盘场景）。
  - 陷阱：**上传发生在发送之前，`messageId` 在发送时才由网关生成** → 需要「发送成功后回填」或「网关在持久化用户消息时顺带认领同 requestId 的产物」，并处理发送失败 / 重试 / 多端重发的重入。
- **路线 3 · 文本挂钩（最轻，最脆）**
  解析已有文本行 `- <fileName> (artifact:<artifactId>)`（`attachment-upload.ts:130-136` 写入）还原 `{fileName, artifactId}` → 渲染卡片，并把该行从正文中剥离（否则文本与卡片重复）。
  - 优点：**零跨包改动**，纯 `apps/web`，可立刻交付 80% 的用户价值；卡片组件与路线 1/2 完全一致，日后升级只换数据源不改 UI。
  - 代价：从文本反解结构化数据，属权宜之计，**必须加契约测试锁死该文本格式**（格式一改卡片即静默失效）；且该行仍会进模型上下文（现状已如此，不新增问题）。

**倾向（待用户拍板）**：先做**路线 3** 落地卡片 UI 与取数层，并把它登记为「临时数据源」+ 契约测试；同时把**路线 1** 记为后续独立立项（届时只替换数据源）。理由：P1 的目标是让用户「看得见、点得动」文件，路线 3 能在最低风险下达成，而路线 1 的跨包改动不适合与 P1-A 同期进行。

### D-2 图片尺寸与裁切

- 1 张：宽度 100%（容器内最大 460px）、16:10、`contain`；
- ≥2 张：`cover`，1:1（3 张时主图跨 2 行）；
- 是否接受 1 张图不再强制裁切成方形（会改变现有观感）→ 待确认。

### D-3 音频假波形

建议**下线** `Math.sin` 装饰柱，改为与视频一致的进度条（已列入 P2）。需确认是否有产品/演示依赖该视觉；若无异议则 P2 一并处理。

### D-4 hover 徽标 → 操作条

现状 hover 只出 ⤢ 徽标；本次计划改为「下载 / 放大 / 更多」三键。是否保留 ⤢ 或改用图标语言一致的符号，待确认（不影响主体逻辑）。

### 关键实现决策

1. **布局解算下沉为纯函数**：多分支 + 边界（`0` / `1` / `3` / `>9` / 非法输入）放在组件里只能靠渲染快照间接验证，抽出来后逐分支可断言。
2. **移除 `hoverIndex` state**：hover / focus 表现改由 CSS `:hover` / `:focus-visible` 承担，减少无意义 re-render；徽标仍是无内联 `style` 的 class 元素（既有断言继续成立）。
3. **下载按钮与缩略图按钮同级**：`<button>` 内嵌 `<button>` 是非法 HTML 且会让点击语义二义；既有测试本就断言「交互元素不得嵌套」，故采用同级元素 + 绝对定位覆盖。
4. **缩略图按钮不加 `aria-label`**：文件名按钮已占用「放大查看 X」，同名会让按 name 查询命中多个；缩略图沿用 `title="点击放大查看"` 作为可见名称（既有测试按 title 取元素）。
5. **缩略图条复用 `goToIndex`**：自动继承「边界 no-op、不循环、不把相同索引回抛受控调用点」的既有语义，无需新增分支。
6. **hover 压暗用 `color-mix(in oklch, black 32%, transparent)`**：该 CSS 文件被测试断言禁止出现 `rgb()` / `rgba()` 字面量，而遮罩色在 token 表里确无对应变量（与 `image-lightbox` 遮罩属同一处例外）。

### W1 · 媒体层颜色收敛（D-9）+ `variant` 死路径清理

成员 `impl-media-tokens`。此前 D-9 把「既有硬编码颜色收敛」推迟到本期。

**关键判断（不是机械替换）**：

- `AudioPlayer.tsx` 里的 `rgba(...)` / `#hex` **大多是 `var(--token, fallback)` 的兜底字面量**，属于刻意的优雅降级 → **保留**，不视为待收敛项。

**新增 9 个媒体层 token**（`packages/shared-ui/src/tokens.ts`，沿用 `var(--x, fallback)` 房子风格；fallback 即原硬编码值，故**视觉等价由构造保证**，无需逐像素比对）：

| token | 值 | 覆盖 |
| --- | --- | --- |
| `mediaScrim` | `#000` | letterbox 底 |
| `mediaGradient` | `rgba(0,0,0,0.6)` | 控件栏渐变底 |
| `mediaBadgeBg` | `rgba(0,0,0,0.5)` | 格式角标底 |

| `mediaTextSubtle` | `rgba(255,255,255,0.6)` | 时长 |

### W2 · 桌面端导出一致性（这其实是**缺陷**，不只是「重复代码」）

成员 `impl-export-blob`。复查曾把「下载套路重复」列为代码坏味；追下去发现是**跨端行为不一致**：仓库已有 `utils/export-file.ts`（桌面端 Tauri 走**原生保存对话框**），但消息内文件卡片自造 anchor → **桌面端不弹原生框**，与其余导出一致性破裂。
