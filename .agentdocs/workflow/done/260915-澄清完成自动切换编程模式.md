# 澄清模式「设计完成 → 自动切换到编程模式」

> **日期**：2026-09-15 ｜ **状态**：已实现并验证，待提交 ｜ **范围**：A 层（chat 澄清模式）+ web-client + web + 提示词规范
> **关联**：`.agentdocs/workflow/260914-grill-clarification-enhancement.md`（G6 确认门控 / A 层澄清链路）、内置 skill `agentdocs-orchestrator`

---

## 1. 任务概览（Task Overview）

两件事：

1. 澄清模式（`dialogueMode='clarify'`）原本只做到「产出方案 + 提示用户手动切换到编程/程序员模式」，会话元数据始终停留在 `clarify`；本次让「设计已完成」在机器可判定的门控上**自动切换到编程模式**。
2. 澄清模式产出的方案文档改为**按 agentdocs-orchestrator 工作流规范组织**（`.agentdocs/workflow/` 落盘路径 + 复杂度评估 + `T-XX` 原子任务 + 验证契约），使其可被 `/start-work` 与工作流索引直接消费。

## 2. 现状分析（Current Analysis）

- `DIALOGUE_MODE_SYSTEM_PROMPTS.clarify` 的【方案输出】只要求「目标、约束、功能清单、技术选型、实施步骤、风险点」，与 `.agentdocs/workflow/` 既有文档结构（现状 / 设计 / 复杂度评估 / 分期任务 / 验证 / 风险 / 非目标）不一致。
- 澄清模式是**只读**模式（`CLARIFY_MODE_ALLOWED_TOOLS` 不含 write/edit），方案文档只能先在对话里定稿——落盘必须由后续模式完成。
- 项目已有消费方按 `.agentdocs/workflow/` 发现计划：`/start-work`（`command-templates.ts`）、boulder 计划发现、工作流运行态 `activeWorkflowPlanPath`。方案文档不符合该结构就无法被这些链路复用。
- 澄清链路的"设计完成"信号此前没有任何服务端动作：`clarificationState.confirmedAt` 只落库，不改模式。

## 3. 方案设计（Solution Design）

### 3.1 触发门控（机器可判定，二选一）

| 门控 | 含义 | 判定点 |
| --- | --- | --- |
| `clarification_confirmed` | grill 确认节点 `__grill_confirm__` 被用户肯定回答，`clarificationState.confirmedAt` **首次**落库 | `routes/questions.ts` → `updateSessionClarificationState()` |
| `plan_approved` | `ExitPlanMode` 审批通过（`Start implementation`） | `routes/questions.ts` → `updateSessionPlanModeForExitDecision()` |
| `user_confirmed` | 用户点击 chat 顶栏「确认转换」按钮（手动逃生口，不依赖任何门控） | `routes/session-dialogue-mode.ts` → `POST /sessions/:id/clarify/confirm` |

两者都在同一入口 `POST /sessions/:id/questions/reply` 判定，**在返回 HTTP 响应前同步完成切换**，前端紧随的快照刷新不会读到旧值。

### 3.2 关键决策

1. **SSOT 在网关元数据**：切换 = `sessions.metadata_json.dialogueMode → 'coding'`，并写审计字段 `dialogueModeSwitch: { from, to, reason, at }`（reason ∈ `clarification_confirmed` / `plan_approved` / `user_confirmed`）；所有来源（自动门控 + 界面手动确认）都走同一个 `switchSessionDialogueModeToCoding`，前端只做同步展示，不参与判定。
2. **不新增 `DialogueMode` 枚举**、不新增表、不新增 RunEvent 类型；新模式经回复响应字段 `dialogueMode` 回传。
3. **不切换**：非 `clarify` 模式；带 `clarificationIntent` 的 team reception 澄清链条（由 handoff 编排器推进）。
4. **通道**：web-client `reply()` 返回 `QuestionReplyResult`；web 用 window 事件（`dialogue-mode-events.ts`）广播给持有模式状态的页面（回答入口分散在 chat inline 面板 / 全局待办面板 / 会话状态 hook）。
5. **本轮恢复的请求沿用原请求模式**：共识确认那一轮仍按澄清提示词输出最终方案文档，模式切换对**用户的下一条消息**生效。
6. **确认节点选项同步**：模型给出的确认题选项文案先同步进引擎确认节点再判定（`applyAnswer` 只认字面量 `confirmed` 或推荐项标签，否则"确认"会被误判成"驳回"）。
7. **终局确认轮兼容**：确认题不参与决策节点构造（避免与引擎节点重名），并允许"只有确认题、没有新决策节点"的轮次。
8. **方案文档对齐 `agentdocs-orchestrator`**：澄清轮产出该结构（只读，不落盘）；切换到编程模式后第一步落盘 `.agentdocs/workflow/YYMMDD-<中文任务名>.md` + 在 `index.md`「当前进行中的任务」登记，完成后归档 `workflow/done/`。复杂度评估（Direct / Lightweight / Full orchestration）与 `T-XX` 原子任务是硬要求。

## 4. 复杂度评估（Complexity Assessment）

| 信号 | 计分 |
| --- | --- |
| 原子步骤：T-01…T-12 共 12 项 | +2（5+ 步） |
| 多模块（services/agent-gateway、packages/web-client、apps/web、.agentdocs） | +1 |
| 结果需持久化供他人复查（workflow 文档 + index 登记） | +1 |
| 可用原生 `task()` 派发（Mode A 可用） | –1 |
| 独立并行流 | 0（链路强依赖，无并行收益） |
| 单步 >5 min | 0 |
| **合计** | **3 → Full orchestration**（workflow 文档；执行按 Mode B 在上下文顺序推进，未建 `runtime/` 目录——任务链强依赖，串行执行无并行收益） |

> 路由结论：Full orchestration 的**文档要求**（workflow 文档 + 分期任务 + 验证契约）已满足；执行方式选择 Mode B（串行），因为后续任务逐项依赖前一项的接口与提示词结论。

## 7. 风险与缓解

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 模型未按保留 nodeId 提问 → 门控不触发 | 自动切换失效 | 提示词硬约束 + 提示词契约测试；模式选择器保留手动逃生口 |
