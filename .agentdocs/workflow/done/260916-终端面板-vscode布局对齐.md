# 260916-终端面板-vscode布局对齐

## Task Overview

把底部「终端」抽屉从「单窗格 + 单行 tab 条」升级为 **VS Code 集成终端面板**布局：

1. **P1 布局骨架**：面板级页签（`终端` / `端口`）+ 右侧操作区（新建▾ / 拆分 / 取消拆分 / 重命名 / 关闭其他 / 清屏…）+ design token 合规重绘
2. **P2 分屏**：**嵌套任意方向**拆分 + **拖拽分隔条** + **拖拽重排** + **把多个终端 tab 合并进一个分屏布局**
3. **P3 端口页**：监听端口列表（Port / 进程 / 地址 / 可见性 / 操作）
4. **P4 真端口转发**：VS Code PORTS 同款（**网关侧全新基建**，见 Risks）

**入口范围（用户已确认）**：**只改底部「终端」抽屉**（`TerminalPanel` → `QuickTerminalPanel`）；`SessionTerminalsPanel` chip 弹层不改。

## Solution Design

### 核心决策（Oracle 咨询后定稿）

- **D1 — 树的叶子是「组」（VS Code 的 group），不是单个终端**。`TerminalPaneNode { kind:'pane'; id; terminalIds: string[]; activeTerminalId }` 持有 tab 列表；`TerminalSplitNode { kind:'split'; id; direction:'row'|'column'; children:[A,B]; ratio }` 组合组，**严格二元**、`ratio` 钳制 `[0.1, 0.9]`；`TerminalLayout = Node | null`（`null` = 单组无分屏）。
  理由：这样「每个组一条 tab 条」直接复用现有 tab 逻辑（rename / close / 自动移除 / active 解析）；若改成「全局一条 tab 条 + 单终端叶子」反而要发明 tab↔pane 映射，制造第二套真相。
- **D2 — 三套真相的收敛规则**：`useSessionTerminals.terminals` 是**唯一的存在性/状态真相**；`TerminalLayout` 是**纯排布描述**（只引用 `terminalId`，永不决定终端是否存在）；tab 条是**派生值**（不在树里的终端 → 渲染成 tab；在树里的 → 提升为 pane）。
- **D3 — split 默认新建终端，拖 tab 才是合并**：`split` = `POST` 新建持久终端（VS Code 行为）；把 tab 拖进 pane = 合并已有 `terminalId`。**禁止「空 pane」**（`terminalIds: []` 是非法态）。
- **D4 — 焦点瞬态、组内激活持久化**：`activePaneId` 放**瞬态 state**（焦点短暂，持久化只带来脏数据）；每个 pane 的 `activeTerminalId` 持久化在树里。用一个 `TerminalLayoutContext`（React 19 `<Context value>`）供递归渲染器 + 全局快捷键 + 拖拽态共享。
- **D5 — SSE：每个挂载的 pane 一条，不 unmount 非激活 pane**。unmount 会丢 scrollback 并触发 `term.reset()`（replay 只保 512KiB ring，TUI 会花屏）。**pane 上限 4，硬顶 6**。抽屉收起本身就卸载全部（天然上界）。
- **D6 — 渲染与移动**：递归 `<TerminalPane key={node.id}>`，内部 `<InteractiveTerminalView key={node.terminalId}>`；**跨 pane 移动必然 remount**（React 跨父节点即卸载），接受，代价 = 一次 ring 回放。
- **D7 — resize 节流 + 零尺寸守卫**：拖拽期间 `fit()` 本地每帧（廉价、保证渲染正确），但 `resizeTerminal` POST 做 **~120–200ms trailing debounce**；并新增守卫：`cols < 2 || rows < 1` 时**跳过 POST**（隐藏/零尺寸 pane 会算出 cols=0 并刷 resize）。
- **D8 — 持久化键复用既有推导**：布局按**会话**存，键必须复用 `terminalPanelSessionKeyFor(lastChatPath)`，**不得**另造 sessionId 键（否则同一会话两把钥匙）；`version 24 → 25` + 载入期结构校验；归一化纯函数 `normalizeLayout(layout, liveIds, { maxPanes })`。

### ⛔ 三处前提纠正（Oracle 指出，必须前置处理）

1. **缺的 `location` 在 nginx，不在网关**：`apps/web/nginx.conf` 是**路径白名单**（仅 `/`、`/api/`、`/auth/`、`/sessions/`）。新增 `/ports/*` / `/pub/*` 若无对应 `location`，会被 `location /` 的 SPA `index.html` 吃掉。这是 P4 的硬前置，属 **nginx 配置**问题。
2. **「枚举宿主机端口」在 Docker 拓扑下提法本身是错的**：`docker-compose.yml` 用 bridge + `3000:3000`，gateway 在容器 netns 内，`/proc/net/tcp` **看不到宿主机**。但真正该枚举的种群是「**agent 在 gateway 同 netns 内起的端口**」——agent 经 bash 工具跑的 `npm run dev` 就在该 netns 里。这反而让设计自洽：目标种群 = gateway 命名空间内的监听端口。
   另：**桌面同机场景「直接打开 `localhost:PORT`」就是完整功能，不是降级**。
3. **分屏在 `pnpm dev` / CLI（Node）下会「看起来是坏的」**：Node 与 Windows 降级 pipe，`resize` 是 **no-op**。更麻烦的是 `toPublicTerminal()`（`routes/session-terminals.ts:90`）**把 `metadata` 剥掉了**，而 `persistent-terminals.ts:230` 恰好写了 `metadata.backend` → 前端**无法知道**自己能不能 resize。**分屏必须先补上 `backend` / `supportsResize`（加法扩展）**，否则 Node 下分屏静默不生效。

### ⚠️ 最危险的交互（必须在实现前设计好）

`normalizeLayout` 若在 `useSessionTerminals` **切换会话瞬间的空 map** 上执行，会判定「所有终端都不存在」→ 清空该会话的持久化布局；**若此时又持久化，就变成「每次切会话永久销毁用户布局」**。
缓解（强制）：① 只在**用户主动变更**时写持久化，**禁止**任何「归一化后自动落盘」的 effect；② 归一化门控 `layoutReady = !loading && lastSyncedAtMs !== null`；未 ready 时按持久化原样渲染（占位/骨架），不做归一。


### 已验证事实（本机实测）

- 网关运行时三态：dev `tsx`（Node）/ CLI `node dist/index.js`（Node）/ 桌面 sidecar（Bun，`bun build --compile`）。
- **Bun 原生 PTY 仅 POSIX**；`TerminalProcess.resize` 在管道后端返回 `false`（无 SIGWINCH）。
- 生产拓扑：`浏览器 → Caddy(TLS/HTTP3) → web(nginx) → gateway:3000`；桌面 sidecar 与 webview **同机**。
- `browser-live`（Playwright 实时视图 over WS）是既有先例，但**仅桌面 sidecar** 可用。

### 📌 端口轨道：因安全评审不通过而收敛为方案 C

**决策依据**：`t16-port-forward-preconditions.md` 的安全评审结论为**不通过（4 项 blocker）**，且发现两处前提失效：

1. **B1 同源托管（根本性）**：路径前缀代理把被代理应用放在**与主应用同源**上 → 其任意 XSS 可读 `localStorage['auth-store']`（含 7 天 `refreshToken`）→ **账号接管**。`pf_<id>` 的 HttpOnly + Path 隔离只保护 pf cookie，保护不了主会话 —— 文档 §3「路径级隔离」的核心前提不成立。
2. **§4「Vite/Next 应用可用」与事实冲突**：`forwardId` 在**创建转发时**才生成，而 `base` 必须在 dev server **启动前**写死；且 Vite 的 HMR WS 指向 `/@vite/client`（不含前缀）→ 落到 `location /` → cookie Path 不匹配 → **HMR 失败**。即真代理对最主要的使用场景可能根本不可用。

其余 blocker（B2 上游响应头未剥离 → SW scope 提权可持久化 MITM `/api/*` / cookie bomb 同源 DoS / HSTS / `X-Accel-Redirect`；B3 无 denylist → 仅凭 pf cookie 可访问网关无鉴权的 `/metrics`、`/docs/openapi.json`，也可打 Redis；B4 `pf_<id>` 对上游进程可见）与 9 项 should-fix 均记录在评审输出中，**作为将来若重启该轨道的前置清单**。

**方案 C 的范围**：
- **保留并采用** T-14（枚举，已交付并验证）+ T-15（端口页 UI：列表 + 「在浏览器打开」）
- **桌面/同机**：直接打开 `http://localhost:PORT` —— Oracle 明确「**这就是完整功能，不是降级**」
- **远端部署**：动作禁用并明示「需要反向代理，当前未启用」
- **零代理代码、零新增攻击面**；`public` 可见性、任意 host、任意 TCP 均不做
- 若将来重启真代理：必须先选 **独立 origin**（子域/独立端口）或 **CSP `sandbox`** 并过复审——**这是产品决策，不是实现细节**
