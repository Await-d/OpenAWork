## 一、问题

同一条「工具名 → 渠道能力分组」规则在**前后端各有一份手写实现**，已发生漂移：

- 后端 `services/agent-gateway/src/channels/channel-capability-tool-groups.ts`（162 行，`switch` 为主）
- 前端 `apps/web/src/components/common/display/channel-capability-tool-groups.ts`（340 行，pre-switch `if` 链 + `switch`）

漂移实例：委派工具规范名 `subagent` **只在一侧登记** → 前端能力目录把它归入 `other`，后端归 `orchestration`；`capabilities.ts:451` 用分组结果做能力**过滤**，因此渠道「按组开关」语义错位。此外两端各自声明了同名类型（分组键、注入开关），其中注入开关的**可选性语义已不同**（后端可选 / 前端必填）。

## 五、效果与遗留

- **漂移根因消除**：两端现在引用**同一函数对象**（测试用 `toBe` 断言同一性），不再可能"只改一侧"；
- **防回归**：`CHANNEL_CAPABILITY_TOOL_GROUP_CONTRACT` 黄金表保留 `subagent` / `repo_clone` / `repo_overview` 锚点，任一侧漏登记或规则被误改都会立刻失败；
- **形态语义显式化**：注入开关的「可缺省持久化形态」与「归一化形态」在同一处定义派生，前端 UI 保持字段必有；
- **遗留**：`@openAwork/shared` 的 `index.ts` 是 1876 行汇总出口（并行冲突热点），本次仅追加 13 行；如需进一步治理建议后续单独评估"子路径导出"。

## 七、子路径导出评估（2026-11-03 补充，已闭环）

**结论：不实施，仅登记。**

实测依据：

| 项 | 事实 |
| --- | --- |
| `packages/shared/src/index.ts` | 1876 行、**143 条 export 语句**、单入口 `exports: { ".": … }` |
| 全仓使用子路径导入的消费点（`from '@openAwork/shared/…'`） | **0 处** —— 所有消费者（gateway / web / shared-ui / web-client / agent-core / multi-agent / mobile / desktop）都从根入口导入 |

不实施的三条理由：

1. **无消费需求**：子路径导出的收益是"按需加载、避免拉全量模块"。当前消费方式下收益为零，属**无需求驱动的 API 面扩张**；
2. **维护成本真实**：需同步维护 `exports` 映射、（可能的）多 tsconfig 引用与文档，且一旦开放就形成需要长期保持的公共契约；
3. **改动窗口应留给功能变更**：该文件是多任务并行的冲突热点（本次去重是它唯一一次被触碰，仅追加 13 行）。

**重新评估的触发条件**：出现"只需 shared 内某个小模块、却被迫拉全量"的打包/加载实测诉求，或出现需要通过精细出口化解的跨包循环依赖。

## 六、教训

1. **同一规则复制到两处，必然漂移** —— 本次是第二次在 `261102` 系列里遇到"只落一处"（前一次是单侧漏登记名称）；
2. **纯再导出不会在本文件内绑定类型名**：`export type { X } from 'm'` 之后文件内无法引用 `X`，需顶部 `import type` + 本地 `export type { X }`（本次由 `TS2304` 实测暴露）；
3. **`eslint no-fallthrough` 会把相邻 `case` 之间的注释判为 fallthrough** —— 说明性注释应放函数 JSDoc，不要夹在 `case` 标签之间（本次与 M2 在 `261102-修复规范名…` 中踩到的是同一个坑）。
