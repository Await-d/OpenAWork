# 文件提及索引架构（`@` 提及可达任意深度）

## Task Overview

用户报障：输入框里输入 `@` 弹出的文件候选项「无法获取到文件夹内的信息，只能获取到工作区根目录的文件」。随后用户明确了目标架构：**索引在后端缓存，前端不做全量加载，检索由用户输入驱动**。

因此本任务包含两件事：

1. **修复可达性**：`@` 能引用任意深度的文件——`@` 单列根级条目（目录在前，可选中进入），`@apps/web/src/` 逐级进入，`@ChatPage` 按文件名命中深层文件。
2. **修复取数方式**：网关缓存文件索引并在服务端完成检索/排序，前端只渲染当前查询命中的小结果集，不再下载全量清单。

## Current Analysis

现状（已核实源码与实测，非推测）：

- `@` 候选项来自 `useChatDataLoaders` 调 `GET /workspace/tree?depth=2` 后在前端 `flattenWorkspaceFiles()` 扁平化，并在菜单里 `.slice(0, 8)`。
- 结果是「根目录文件 + 根目录下一级文件」，而本仓库的代码都在第 3 层及更深（`apps/`、`packages/`、`services/` 自身没有直接文件）——实测深度 2 的扁平结果第一条是 `.agentdocs/index.md`，`apps/web/src/pages/chat-page/ChatPage.tsx` 一条都拿不到。
- `/workspace/tree` 另有 `MAX_DEPTH=4`、`MAX_ENTRIES=500` 硬上限，单纯调大前端 depth 无法覆盖（本仓库约 1.28 万文件，索引可用 4.4 千）。
- 量级：全量扁平清单约 301KB JSON；单次查询命中结果 68B–1.3KB。全量下发对前端与网络都不合适，这正是用户要求「后端缓存 + 按输入检索」的原因。

复查阶段发现一个**跨工作区根的真缺陷**（本特性放大器）：`ensureIgnoreRulesLoadedForPath` 按根记忆化，而 `defaultIgnoreManager.loadRules()` 把 `projectRoot` 存为进程全局单值——后服务的根会顶掉先前根的规则，锚定 `.gitignore` 规则失效。实测（单进程复刻其记忆化语义）：

```
修复前：A 根单独服务 4433 files / 0 泄漏 → 服务过 B 根后 A 根重建 7113 files / 1007 泄漏
修复后：全局单例故意指向 B 时，A 根索引 4437 files / 0 泄漏
```

同一缺陷在未改动的 `/workspace/tree` 上也可复现（属共享历史缺陷），单工作区部署不受影响。

## Solution Design

**一句话架构：网关侧进程内有界缓存的递归扁平索引 + 服务端「目录逐级 / 相关性排序」检索；前端防抖取消式查询，只渲染命中结果；忽略规则按工作区根隔离。**

### 网关

- `workspace-file-index.ts`：BFS 递归遍历（无层数限制，仅总条目上限），跳过 VCS/构建/工具状态目录、符号链接与忽略规则命中项；返回相对根、`/` 分隔的扁平路径。
  - 缓存：按工作区根键控，TTL 15s、上限 16 个根、超出淘汰最旧；规范化键；缓存对象以 `readonly` 数组对外。
  - 按根隔离的忽略管理器：`getWorkspaceIgnoreManager(root)` 为每个根创建独立 `createAgentIgnoreManager()` 实例（有界缓存、失败不永久缓存），索引构建不再依赖进程全局单例。
  - `ensureIgnoreRulesLoadedForPath` 同步修正为「全局当前根 ≠ 请求根则重载」，惠及 `/workspace/tree` 等既有消费方。
- `workspace-file-search.ts`：纯函数检索。`q` 为空或含 `/` → 目录逐级展开（只回直接子级，目录在前）；否则相关性排序（label 精确 > 前缀 > 子串 > 路径子串；同分文件优先、浅层优先），并复用预计算的 `lowerLabel/lowerPath/depth`，单次查询为一次线性扫描。
- 路由 `GET /workspace/files/search?path=&q=&limit=`：鉴权 → 路径安全 → 白名单 → 忽略 → stat 校验顺序与 `/workspace/tree` 完全一致；`limit` 默认 20、上限 50、`q` 上限 200；超限走既有的中文 `BadRequest`。
- 失效：所有成功的 HTTP 写路径（写文件 / 建目录 / 删除 / 重命名 / review 回滚）显式失效对应根。
- 已删除：`GET /workspace/files`（全量清单端点）——复查确认它零生产消费者，属投机接口。

### 客户端与前端

- `@openAwork/web-client`：仅保留 `searchFileIndexResult`（结果式）供应用使用；不再暴露任何全量清单方法。
- `composer.ts`：`buildMentionItemsFromSearch()` 只把服务端返回的 `files`/`directories` 映射为菜单行（label / 描述 / 插入文本 / `isDirectory`），不在前端做匹配或重排；呈现契约为「目录行在前，文件行在后，各自保持服务端顺序」。
- `use-mention-file-search.ts`：防抖 120ms、中止旧请求、请求序号守卫（旧 query 迟到响应不覆盖新结果）、加载中保留上次结果、失败保留上次结果并暴露 `error`（非 stale 失败写日志）、`hasAnyEntries` 随工作区（`search` 身份）复位。
- 三态齐备：loading（正在检索）/ empty（未找到匹配 / 暂无可引用）/ error（检索失败提示，独立于空态，避免误导）。
- 目录选中写入 `@dir/` 并保持菜单打开继续进入；文件选中写入 `@path ` 并关闭菜单。

### 关键决策

- **不用调大 `/workspace/tree` 的 depth**：其上限语义面向目录浏览，与「一次拿全量供检索」需求不匹配，且树形载荷比扁平路径更重。
- **检索放服务端**：这是用户明确要求（前端不全量加载）；顺带解决「超大仓库前端内存/传输」问题。
- **忽略规则按根隔离而非修补全局单例**：全局单值在多根并发下无解，per-root 实例才是根治；共享 helper 单独修一次以覆盖既有路由。
- **写工具不逐点插桩**：写点有 11 处、横跨 8 个文件且含 `packages/agent-core`，逐点插桩会污染跨包与高频失效（每次只读工具都触发重建）。改为在运行/工具执行的单一咽喉点失效，配合 15s TTL 兜底。
- **限流自包含实现**：网关内无限流先例，不引入新依赖与全局插件，仅在索引检索路由上加一个按「用户 + 工作区根」的滑动窗口软护栏（预算远高于 120ms 防抖产生的真实流量），拒绝时返回中文 `429` + `Retry-After` 且不触发索引构建。

## 验收与验证

- 网关 `src/__tests__/workspace` + `routes/workspace-routes.test.ts`：全绿（含缓存命中/过期/淘汰、跨根隔离回归、浏览/排序/limit、`q` 边界、错误矩阵）。
- `web-client` 全量测试与构建、`apps/web` composer/conversation 全域测试与 `typecheck` 全绿；改动文件 Prettier 通过，网关 ESLint 通过。
- 真实仓库实测：冷 1023ms → 热 0.01ms（返回同一缓存对象）→ 过期重建 1030ms；单次查询响应 68B–1.3KB（全量 301KB）；`@ChatPage` 命中 `apps/web/src/pages/chat-page/ChatPage.tsx` 且排首位。
- 真实浏览器端到端：输入 `@apps/` 弹出 `desktop/ · apps`、`mobile/ · apps`、`web/ · apps`；输入 `@ChatPage` 弹出并可通过点击插入 `@apps/web/src/pages/chat-page/ChatPage.tsx`；网络日志确认只调用 `/workspace/files/search`。
- 跨根忽略规则：修复前 1007 条泄漏、修复后 0；夹具锚定规则在其它根加载前后均正确生效；`ensureIgnoreRulesLoadedForPath` 回到正确根时可重新生效。

## 已知边界与遗留

- 团队页输入框的 `@` 仍为空：团队 composer 未注入检索函数（改动前同样为空，非本次回归）。已具备注入点，需要时接一个 `searchMentionFiles` 即可。
- 绕过网关路由的写（外部编辑器、`git checkout`）与 Agent 写工具由 TTL/咽喉点覆盖，仍存在有限陈旧窗口。
- 忽略目录名单已收敛为单一来源模块，索引与工作区工具 walker 共用。
- `ChatPage.tsx` 体积属既存技术债（远超 1500 行上限），本次仅做装配级改动。
