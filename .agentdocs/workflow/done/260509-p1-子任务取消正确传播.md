# 260509 — P1 子任务取消正确传播

属于 [260509-opencode借鉴升级总览](260509-opencode借鉴升级总览.md) 的 Phase 1。

## Task Overview

修复 `task` 工具（delegate_task / sub-agent）在父会话被 abort 时，**没有正确等待子会话取消完成**的问题。对齐 opencode `75d141b574` (#25798)。

## Current Analysis

opencode 修改要点（diff）：

```diff
- function cancel() { ops.cancel(nextSession.id) }
- ctx.abort.addEventListener("abort", cancel)
+ const cancel = ops.cancel(nextSession.id)         // Effect.Effect<void>
+ function onAbort() { runCancel.fork(cancel) }
+ ctx.abort.addEventListener("abort", onAbort)

  // Release 阶段
- () => Effect.sync(() => ctx.abort.removeEventListener("abort", cancel))
+ (_, exit) => Effect.gen(function* () {
+   if (Exit.hasInterrupts(exit)) yield* cancel       // 父被中断时 await 子取消
+ }).pipe(Effect.ensuring(...removeEventListener(onAbort)))
```

核心改动：父会话被中断（abort）退出 task tool 时，必须 **`await` 子会话取消** 才返回，否则子会话的 stream 可能继续吃 token / 写日志，资源泄露。

OpenAWork 的对应位置：
- `services/agent-gateway/src/task-tools.ts` — task tool 主体
- `services/agent-gateway/src/task-parent-auto-resume.ts` — 父子 lineage 与恢复
- `services/agent-gateway/src/session-runtime-reconciler.ts` — runtime 状态机
- `services/agent-gateway/src/routes/stream.ts` / `routes/commands.ts` — abort 信号源

需要核对：
1. 父会话 abort 时是否 fire-and-forget cancel 子会话？
2. cancel 是否返回 Promise / Effect？是否被 await？
3. 中断退出（vs 正常退出）路径是否区分处理？

## Solution Design

### S1: cancel 信号同步等待

让 `task` 工具的 cancel 路径走"父会话 abort → 调度子会话 cancel → 等子会话 stream runtime 完全清理 → 才让 task tool 返回"：

```ts
// task-tools.ts 伪代码
async execute(args, ctx) {
  const child = await spawnChildSession({...});
  const cancelPromise = () => cancelSession(child.id, { reason: 'parent_aborted' });

  let aborted = false;
  const onAbort = () => {
    aborted = true;
    // 不能 fire-and-forget，但也不能立即 await（会阻塞 abort 处理）
    void cancelPromise().catch(logCancelFailure);
  };
  ctx.signal.addEventListener('abort', onAbort);

  try {
    return await runChildToCompletion(child);
  } finally {
    ctx.signal.removeEventListener('abort', onAbort);
    if (aborted) {
      // 等子会话 runtime 真正释放
      await waitForChildShutdown(child.id, { timeoutMs: 10_000 });
    }
  }
}
```

`waitForChildShutdown` 复用现有的 `session-runtime-reconciler` / `session-runtime-thread-store` 的状态查询，等到子会话不再 `running`/`canceling` 才返回。

### S2: 多层 task 链取消

如果子会话又 spawn 了孙子会话，cancel 必须递归到底。借助 `task_parent_auto_resume_contexts` 表（DATA-014 已建）的 lineage，自顶向下 cancel：

```ts
async function cancelSubtree(rootSessionId: string) {
  const descendants = await listDescendantSessions(rootSessionId);
  await Promise.allSettled(descendants.map(id => cancelSession(id, { reason: 'ancestor_aborted' })));
  await Promise.allSettled(descendants.map(id => waitForChildShutdown(id, { timeoutMs: 5_000 })));
}
```

### S3: 取消理由透出

把 `reason: 'parent_aborted' | 'ancestor_aborted' | 'user_aborted'` 写入 `session_run_events`，供前端展示"任务被父会话取消"而不是显示成"用户取消"。

### S4: 单元/集成测试

- 父会话 abort：子会话不再产新事件、最终 `status=cancelled`
- 父→子→孙：abort 父，孙也 cancel，且总耗时 < 1s（无 hang）
- 子会话 cancel 失败：父 task tool 仍在 timeout 内退出，并报 `cancel_failed` 错误
- 正常完成路径：cancel 监听器被正确解绑（不残留）

## Risks & Rollback

- **waitForChildShutdown timeout 太长**会让 stop 体验变慢：上限 10s，给前端"正在停止…"loading；超时仍 fallthrough，但日志报警
- **cancel 死循环**：递归 cancel 必须做 visited set，避免环（理论上 task lineage 是树，但保护一层不亏）
- 单独可 revert，不影响 P0/其他 P1
