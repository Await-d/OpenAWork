## 1. 任务概览（Task Overview）

P2 四项：

1. **提示词模块化**：把 `stream-system-prompts.ts` 内联的模式提示词拆到 `routes/dialogue-mode-prompts/`（shared / clarify / coding / programmer / index），主文件只保留组合链与占位符并 re-export，公共导入面不变。
2. **长度预算断言**：契约测试新增按模式预算（含约 25–30% 余量）与共享片段总量预算，防止提示词静默膨胀推高 stable 前缀成本。
3. **Web 模式说明同步契约**：新增网关侧契约测试，读取 `apps/web` 模式定义源码，断言三模式 value 与语义锚点同时存在于提示词与 Web 文案，把「两份文案靠人工同步」变成可失败的契约。
4. **`dialogueMode` 缺省兜底评估**：评估后**不采纳**（见 §3.4），保留既有「未指定即不注入模式提示词」语义。

## 2. 现状分析（Current Analysis）

- `stream-system-prompts.ts` 目前约 760 行：共享片段 + 三个模式提示词约 320 行内联在同一文件，与仓库「工具提示词独立成 `<tool>-prompt.ts`」的既有模式不一致；继续增长会接近拆分预警区间。
- 模式提示词没有预算约束：P0/P1 一轮就增加了约 1.3k 字符，后续改动无回归信号。
- Web 的 `dialogue-mode.ts`（`DIALOGUE_MODE_DEFINITIONS`）是提示词行为的 UI 镜像，两侧独立维护、无自动同步检查。
- `resolveStreamInteractionModes` 已有契约测试明确锁定「metadata 与请求都未指定时保持未指定」（`stream-interaction-modes.test.ts:138`）；渠道 / API / legacy 会话依赖该语义（不注入模式纪律、不做工具面收敛）。强行给默认模式会改变这些路径的既有行为。
- 实际长度（提示词文本字符数）：clarify 3126 / coding 1334 / programmer 1665；共享片段合计 729。

## 3. 方案设计（Solution Design）

### 3.1 模块化（P2-1）

```
services/agent-gateway/src/routes/dialogue-mode-prompts/
├── shared.ts       # 四个共享片段常量（SSOT）
├── clarify.ts      # CLARIFY_DIALOGUE_MODE_PROMPT
├── coding.ts       # CODING_DIALOGUE_MODE_PROMPT
├── programmer.ts   # PROGRAMMER_DIALOGUE_MODE_PROMPT
└── index.ts        # DIALOGUE_MODE_SYSTEM_PROMPTS 组装 + 共享片段 re-export
```

- `stream-system-prompts.ts` 改为从该模块 import 并 re-export，保持 `DIALOGUE_MODE_SYSTEM_PROMPTS` 等既有导入路径不变（消费方与测试零改动）。
- **不采用** `.md` 资源文件方案：`tsc` 不搬运非 TS 资源（Dockerfile 已记录 `bash.txt` 同类陷阱），需要新增构建期拷贝与多条运行路径适配，收益（可读性）不抵成本；TS 模块内保持纯字符串数组即可被 Prettier / 契约测试覆盖。

### 3.2 长度预算（P2-2）

并入既有 `dialogue-mode-prompts.test.ts`：

| 预算项 | 当前 | 上限 |
| --- | --- | --- |
| clarify | 3126 | 4000 |
| coding | 1334 | 1800 |
| programmer | 1665 | 2200 |
| 四个共享片段合计 | 729 | 1000 |

超限即视为提示词膨胀信号：需要拆段、下沉 skill 或明确调高预算（调高必须在评审中给出理由）。

### 3.3 Web 同步契约（P2-3）

新增 `src/__tests__/prompt/dialogue-mode-web-sync.test.ts`（网关侧）：

- 用 `node:fs` 读取 `apps/web/src/pages/chat-page/mode/dialogue-mode.ts`（**仅测试期**跨包读取，生产代码零依赖）。
- 断言三模式 `value: '<mode>'` 均存在，且语义锚点两侧同时出现：clarify → `只读`、coding → `最小变更`、programmer → `影响面驱动`。
- 文件缺失时先 `existsSync` 给出「路径已变动，请同步更新本测试」的明确失败信息。

### 3.4 `dialogueMode` 缺省兜底（P2-4）：评估后不采纳

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 在 `resolveStreamInteractionModes` 兜底为 `coding` | ❌ 不采纳 | 破坏既有有意语义（`stream-interaction-modes.test.ts:138` 明确锁定「保持未指定」）；渠道 / API / legacy 会话将被强加模式纪律与工具面收敛，属行为变更而非收口 |
| 未指定时显式拒绝请求 | ❌ 不采纳 | 会破坏渠道与外部 API 调用（它们本就不带模式），兼容性破坏面大于收益 |
| 保持现状 + 记录决策 | ✅ 采纳 | 「未指定 = 不注入模式提示词、不做工具面收敛」是有意契约；若未来需要兜底，应在**会话创建边界**写入 metadata（SSOT），而不是在提示词边界默认 |

## 7. 风险与缓解

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 拆分迁移时文本走样 | 提示词静默变化 | T-06 用长度等价断言（3126/1334/1665）+ 既有契约测试双重校验 |
| R2 | re-export 造成循环引用或导入解析问题 | 运行期报错 | 新模块不反向 import `stream-system-prompts.ts`；单一方向依赖，typecheck + 测试覆盖 |
| R3 | 长度预算过紧，正常改动频繁被卡 | 开发摩擦 | 预算留 25–50% 余量；调高需评审说明（写入测试注释） |
| R4 | Web 文件路径变动导致同步测试误红 | 误报 | `existsSync` 先失败并给出路径更新提示；锚点选取语义稳定短语 |
| R5 | 跨包读取被误认为生产耦合 | 架构误解 | 测试文件顶部注释说明「仅测试期读取，生产零依赖」 |

### 潜在问题清单（Gate 4）

- 拆分后 `stream-system-prompts.ts` 的 re-export 必须覆盖既有全部导出（`DIALOGUE_MODE_SYSTEM_PROMPTS` + 四个共享片段），否则测试/消费方导入失败。
- Web 同步锚点若被 Web 文案改写会失败——这是设计意图（强制同步评审）。
- 预算上限调整只改测试常量，不会影响运行时行为。

### 测试用例清单（Gate 4）

- happy path：三模式长度在预算内；Web 定义含三模式 value 与三个锚点。
- 边界：共享片段合计 ≤1000；Web 文件存在性预检。
- 失败路径：任一模式超预算、锚点缺失、Web 文件缺失 → 测试失败并指明项目。
