## 1. 任务概览（Task Overview）

延续 P0（指令优先级 / 模式回流 / 公共纪律），落地 P1 四项提示词收口：

1. **clarify 单轮题量上限**：frontier 超过 5 项时按「阻塞范围 → 依赖深度」排序取前 5，并说明分批理由；与「一轮成组提问」条目对齐，避免一屏抛完。
2. **clarify 非标准作答结算规则**：部分作答 / 明确跳过 / 「都行」/ 答案与代码事实冲突时的处置，消除模型自由发挥空间。
3. **coding 编辑粒度改写**：把「超过 80 行应分步给出」的输出语义改为编辑语义（单次编辑小而可验证，约 80 行以上分阶段落地）。
4. **programmer LSP 段去重**：`LSP_TOOL_GUIDANCE_SYSTEM_PROMPT`（stable 槽 6）已完整给出工具路由与重命名序列，programmer 的【工具使用策略】改为引用该章节，去掉重复条目。

## 2. 现状分析（Current Analysis）

- clarify 的 frontier 纪律要求「一轮中把整个 frontier 一次性提出」，但没有题量上限；浅层需求展开路径的 5 个层级全进 frontier 时，单轮可能出现 8–10 题。
- 用户「答一半 / 跳过 / 都行」时提示词无规则：节点是否结算、是否重问完全取决于模型即兴判断，会污染 `clarificationState` 与后续轮次。
- coding 的「禁止一次性输出大段未经验证的代码（超过 80 行应分步给出）」是聊天贴码时代措辞；现在主路径是 edit 落盘，阈值应绑定「单次编辑 / 分阶段」而不是「输出」。
- programmer 的【工具使用策略】5 条与 `LSP_TOOL_GUIDANCE_SYSTEM_PROMPT`（`stream-system-prompts.ts:263`，同处 stable 前缀）在工具路由上重复；两处独立维护会漂移。

## 3. 方案设计（Solution Design）

### 3.1 clarify（两处新增、一处对齐）

- 【frontier 提问纪律（核心）】：
  - 原「一轮中把整个 frontier 一次性提出」改为「一轮中把本轮要问的问题成组提出；单轮最多 5 题」，与新增上限条目对齐。
  - 新增「单轮提问上限 5 题」：frontier 超限时按「阻塞范围 → 依赖深度」排序取前 5，并先说明「本轮先问这批，剩余 N 项下一轮继续」。
  - 新增「作答不完整时的结算规则」：部分作答 → 已答项结算、未答项留 frontier 且缺依据的下一轮重问；明确跳过 → 按推荐项暂定并标注；「都行 / 你决定」→ 采纳推荐项结算，不重复追问。
  - 新增「答案与代码事实冲突」：以可验证的代码事实为准，先指出冲突并请用户确认，再结算节点。
- 【使用 AskUserQuestion 工具提问】：首条同步为「最多 5 题」。
- 不新增段落，全部并入既有章节，控制 stable 前缀增量。

### 3.2 coding（1 条改写）

- 禁止事项中「禁止一次性输出大段未经验证的代码（超过 80 行应分步给出）」改为「禁止单次堆叠大段未经验证的改动：单次编辑尽量小而可验证；超过约 80 行的改动必须分阶段落地，每阶段验证后再继续」。

### 3.3 programmer（1 段去重）

- 【工具使用策略】改为：语义查询 / 重命名引用「Codegraph / LSP 工具使用策略」章节（不重复工具清单与 rename 序列）；保留影响评估（grep + read）、实现（edit / patch + lsp_touch）、验证（bash + lsp_diagnostics）三条非重复条目。

### 3.4 契约测试（`dialogue-mode-prompts.test.ts` 新增 3 例）

- clarify：包含「单轮提问上限」「作答不完整」「都行」。
- coding：包含「分阶段落地」，且不再包含旧措辞「超过 80 行应分步给出」。
- programmer：包含「Codegraph / LSP 工具使用策略」引用。

## 7. 风险与缓解

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 题量上限让 frontier 较大的需求多耗一轮 | 轮次增加 | 上限只在 frontier >5 时生效；排序保证先问阻塞范围最大的节点，整体轮次通常不增 |
| R2 | 「按推荐项暂定」被模型滥用成静默推进 | 用户决策被绕过 | 仅在用户**明确跳过**或答「都行」时适用，且必须标注；缺依据仍留 frontier 重问 |
| R3 | programmer 去重后 LSP 策略实际缺失 | 工具使用退化 | 引用的是同一 stable 前缀内**本轮必然注入**的 `LSP_TOOL_GUIDANCE_SYSTEM_PROMPT`；契约测试锁定引用短语 |
| R4 | 删除旧措辞破坏既有断言 | CI 红 | T-05 同步跑 3 个 prompt 相关测试文件，并新增负向断言锁定旧措辞不回归 |

### 潜在问题清单（Gate 4）

- clarify 两处修改需语义一致（「最多 5 题」与「单轮提问上限 5 题」），避免模型在两条规则间摇摆。
- programmer 引用章节名必须与 `LSP_TOOL_GUIDANCE_SYSTEM_PROMPT` 首行完全一致，否则模型找不到章节；契约测试只锁短语「Codegraph / LSP 工具使用策略」。

### 测试用例清单（Gate 4）

- happy path：clarify 上限与非标准作答短语存在；coding 新措辞存在；programmer 引用短语存在。

- 失败路径：任一片段缺失 / 旧措辞回流 → 契约测试失败并指出模式。
