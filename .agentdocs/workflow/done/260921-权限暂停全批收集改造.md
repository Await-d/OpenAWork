# 260921-权限暂停全批收集改造

> 状态：**实施中**（Gate 1 已放行 2026-09-21；D-1=路线 B，D-2=只读门控；Phase 0–1 已交付，Phase 2 前端待做）
> 复杂度：**Full orchestration**（score +6，见下）
> 影响面：`services/agent-gateway`（routes / tool-sandbox / permission / message-v2）、`apps/web` + `packages/shared-ui`、`packages/shared`、`services/agent-gateway-dotnet`（平行实现）

## Task Overview

把「批量工具 + 权限暂停」的语义从「串行遇阻即 break 整轮」改为
**同批工具按 tool_use 顺序执行 / 权限无关兄弟继续跑 / 整批全部落定后才向上游发起下一次请求**，
并保证上游 `tool_result` 顺序严格等于 `tool_use` 顺序（prompt cache 前缀稳定）。

用户原始诉求（原话）：

> 并发工具类型的时候，按照先后顺序加所有工具执行完成后统一再发送到上游对话中，而不是不会等待的问题。

**现状确认（已核实）**：顶层多工具是**串行**且权限一出现就 `break`，后续兄弟**根本不执行**；
`batch` 工具内部虽 `Promise.all` 并发但结果被扣住等审批。两条路径都**不会**「卡住的没结果就直接走」，
但也**都会丢失未执行的兄弟**（渲染成 `[Tool execution was interrupted]`）。

**对照实现**：`temp/opencode`（sst/opencode fork，`anomalyco/opencode` dev，commit `88c6c7abc7`）已采用
「工具 fiber 内阻塞 await 权限 + `FiberSet.awaitEmpty` 整批屏障」，是本方案的**目标形态**，
但**不能照抄**——见 Current Analysis §C 的承载约束。

## Current Analysis

### A. 现状行为（用户两问的答案）

| 问题 | 现状结论 |
| --- | --- |
| 一个工具卡权限，其他批量工具会先跑吗？ | **否**。`executeToolCalls` 串行（`routes/stream.ts:1597`），`stream.ts:1936-1946` 遇 `pendingPermissionRequestId` 即 `hasPendingPermission=true; break` → 后续兄弟不执行 |
| 并发取结果会「谁好了先走」吗？ | **否**。结果 in-place 更新到 tool_use 位置已创建的 ToolPart（`stream.ts:1865`），下一轮只在 `executeToolCalls` 返回后构造（`stream-runtime.ts:669` → 回环）→ 顺序由 part 顺序（= tool_use 顺序）决定 |

结论：**顺序与「整批 barrier」现状已成立**；真正缺的是「**权限无关的兄弟不丢**」。

### B. 三个硬阻塞（裸改 `break`→`continue` 必坏）

1. **resume 盲目截断**：`continueFromApprovedToolResult` 写入被批准结果后调用
   `truncateSessionMessagesAfter(resumedResult, inclusive:false)`（`routes/stream-runtime.ts:423-428`）
   → 会删掉写在 pending 结果之后的兄弟结果 → 兄弟 part 回退 → 渲染成 interrupted。
2. **pending payload 是单工具**：`ApprovedPermissionResumePayload` 只有单个 `toolCallId/rawInput`
   （`routes/stream.ts:685-693`）；`ensurePermissionForTool` 按 `(category, scope)` 去重
   （`tools/tool-sandbox.ts:5820` + `5530-5540`）→ 同 scope 的多个待批兄弟共用一行 pending，
   `updatePendingPermissionPayload` 只留最后一个 → 只有一个可 resume。
3. **拒绝级联是会话级**：`routes/permissions.ts:497-529` 拒绝一个 = 同会话所有 pending 全拒
   → 一回合残留多个 pending 会误伤其它回合。

### C. 运行承载约束（决定路线选择 —— 关键）

OpenAWork 的 run 生命周期**绑在 SSE 请求上**：`routes/stream.ts` 即请求处理器，`stream-runtime.ts` 是 resume 运行时，
另有 `registerInFlightStreamRequest` + runtime thread 心跳。请求返回即 run 结束。

opencode 之所以能用「真阻塞 await」，是因为它的 run 是**与请求解耦的 durable drain**
（`temp/opencode/packages/opencode/src/session/prompt.ts:1088-1130` 的 `while(true)` 后台 runner + `SessionExecution.wake`）。

因此：

- **路线 B（保留 pause-and-return + 全批收集）**：零运行承载改动，达成用户诉求，**风险最小**。
- **路线 A（真阻塞 await，对齐 opencode）**：需先证明 SSE 可长期持有，或先落地后台 runner；
  否则进程重启即丢失等待中的工具。

### D. 已核实的前端假设（改造面）

  （后端 `isError:true` + 「等待审批」文案）计入 `completedCount`/`errorCount` → 头部错显「N/N 完成 / 1 失败」。
- `apps/web/src/components/conversation-runtime/messages/message-coercion.ts:3-18`：`hasActivePendingPermissionRequest`

  「有任一 pending 即整轮 paused」需区分「仅某子调用待批」。

## Solution Design

### 路线 B（推荐，默认执行）

保留 `pause-and-return`，但把「遇阻即 break」改为「**同批继续执行 + 全量收集 + 批末统一 pause**」，
resume 时执行该 pending 下**全部**被阻塞调用。达成「顺序 + 全批 barrier + 兄弟不丢」，且零运行承载改动。

- **D1 停轮语义**：`executeToolCalls`（`stream.ts:1532-1950`）的 `break` 改「记录 + `continue`」；
  返回值由 `{hasPendingPermission}` 扩为 `{hasPendingPermission, pendingToolCallIds: string[]}`；
  批末统一返回，caller（`stream.ts:3082`、`stream-runtime.ts:690`）仍据此发 `done: tool_permission` + `paused`（**不发上游**）。
- **D2 兄弟放行范围**（Gate 0 决策 D-2）：推荐**只读门控** —— 只放行只读/无副作用兄弟
  （read/list/grep/glob/只读 MCP），有副作用（write/edit/bash/task）保持「不执行、等审批」。
  理由：模型可能发有前置依赖的调用（如 `[读配置, 删库]`）；opencode 的并发依赖「并行调用互相独立」的协议契约，
  而 OpenAWork 未在 system prompt 中声明该契约。
- **D3 payload 升级**：`request_payload_json` 增 `blockedToolCalls: Array<{toolCallId, toolName, rawInput}>`；
  `updatePendingPermissionPayload` 追加而非覆盖；`permission-contract.ts:106-172` 的
  `parseApprovedPermissionResumePayload` 返回列表（**必须兼容旧单工具 payload**）。
- **D4 resume 批执行**：`resumeApprovedPermissionRequest`（`stream-runtime.ts:772-850`）由「执行单个 `payload.toolCallId`」
  改为「按 tool_use 顺序执行该 pending 下全部被阻塞调用」，逐个落库；
  `resumeRejectedPermissionRequest`（`:857`）对每个被阻塞调用写一条错误结果。
- **D5 截断收窄**：`continueFromApprovedToolResult`（`stream-runtime.ts:112`）的 `truncateSessionMessagesAfter`（`:423-428`）
  改为**只替换本工具结果、不删其后消息**；幂等靠 `replaceExisting`
  （`createToolResultRequestId(clientRequestId, toolCallId)`）+ part 状态守卫。
- **D6 多 pending 闸门**：`permissions.ts` reply 后，仅当「本回合（同 `clientRequestId`）无残留 pending」才 resume，
  否则保持 `paused`；级联 reject 收窄到同 `clientRequestId`；并发 resume 由现有
  `getAnyInFlightStreamRequestForSession` 拦截，并改为「排队/忽略」而非抛错。

### 路线 A（长期对齐 opencode，Gate 0 通过后另立 Phase）

把权限改为**工具内真阻塞 await**（对应 `temp/opencode/packages/opencode/src/permission/index.ts:98-106` 的 `Deferred.await`），
`executeToolCalls` 改并发（`Promise.allSettled`），删除 `hasPendingPermission`/`break`/resume 单工具重放/`truncate`。

- **前置条件**：完成 §C 的承载核实（T-03）—— SSE 可长期持有 或 落地后台 runner。
- **收益**：三个硬阻塞从根上消失（没有 resume 重放）。
- **成本**：承载改造 + 前端 `paused` 语义迁移 + `.NET` 同步。

### D7 明确排除本轮范围

- `batch` 工具「批准后重跑整批导致重复副作用」的既有隐患：**单独成方案**（本方案只保证不为它引入新问题）。
- `.NET` 平行实现的完整功能对齐：本轮只做**语义标记 + 最小同步**，完整对齐另立。
- 工具**真并发**（无界并发 / 资源隔离）：路线 B 下顶层保持串行（推荐）；真并发仅作为路线 A 的一部分。

## Acceptance Criteria

1. 一批 `[只读A, 需权限B, 只读C]`：A/C 执行并落库，B 等待，**不发上游请求**。
2. 批准 B 后：B 执行，A/B/C 的 `tool_result` 按 `tool_use` 顺序**一次性**进入下一轮上游请求。
3. 拒绝 B 后：B 为错误结果，A/C 结果保留且顺序不变（不被截断清除）。
4. 同 category+scope 两个待批调用：一条 pending 行、批准后**两个都执行**。
5. 同一 DB 状态两次渲染 `toModelMessages` 输出**逐字节一致**。
6. `pnpm --filter @openAwork/agent-gateway test` 全绿（含新增验收脚本）。
7. 前端批次头部不再把待审批子调用显示为「完成 / 失败」。

### 深对齐（轮次重放降级为历史驱动，2026-09-21 已实施）

**背景修正**：`payload.nextRound` 实为暂停时的 `round + 1`（`stream.ts:3115` 的 `createStreamExecutionContext(clientRequestId, round + 1, ...)`），即**下一次要跑的轮次**，而非重放点。因此「轮次重放」的风险仅存在于「同一 `nextRound` 被两次续跑复用」——已由问题 1 的守卫挡住。

**调整**：新增 `deriveResumeRound()`——从持久化投影推导下一轮（中间 assistant 消息键为 `${clientRequestId}:assistant:<n>`，故 `next = max(n) + 1`），`payload.nextRound` **降级为兜底**：
- 正常路径：推导值 == `payload.nextRound`，行为逐字节不变（两个验收脚本仍报 `round=2`）。
- 异常路径：即便守卫被绕过，推导值也不会复用已存在的轮次 id，从根上避免重放。
- `continueFromApprovedToolResult` 的循环起点与首轮判定（`beforeUpstreamCall` 门控）改用 `resumeStartRound`。

**验证**：新增 2 条单测锁定契约（有 `:assistant:3` → 推导 4，忽略 fallback 2；无可推导轮次 → 回落 fallback）；单测 12/12、`test:batch-permission` 2 脚本 ok、R7 六套件 39/39、ESLint 0 error。
