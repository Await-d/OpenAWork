# .agentdocs/workflow/260507-web-图片生成工作台实施.md

## Task Overview
在 Web 左侧导航新增一个专用“图片生成”页面，作为独立于聊天页的图片工作台，集中承载文生图、基于已有图片继续编辑、结果历史与产物联动能力。

## Current Analysis
- 当前图片生成/编辑能力主要内嵌在 `ChatPage` 的图片模式中。
- 左侧导航由 `components/layout/RailIcon.tsx` 与 `components/layout/NavRail.tsx` 定义，路由由 `App.tsx` 与 `routes/preloadable-route-modules.ts` 接入。
- 现有前端图片请求主链路已封装在 `pages/chat-page/use-chat-image-generation.ts`，后端仍以 `sessionId` 为核心上下文。
- 当前会话图片复用能力已存在：可从当前会话 content artifacts 选择参考图继续编辑。
- 后端当前边界仍是单参考图编辑，不包含 mask / 多图编辑；专用页面需显式沿用这个限制，不能静默扩 scope。

## Solution Design
推荐新增 `/images/:sessionId?` 专用页面，并在左侧导航增加“图片”入口。

当前确认的产品决策：采用“完全独立”的图片工作台 session 策略。图片页维护自己的 session 与图片历史，不直接复用普通聊天 session。

页面设计建议：
1. 顶部为图片模型与参数控制区，复用现有 `useChatImageGeneration` 与 `ChatImageGenerationControls`。
2. 中间为大尺寸提示词输入与操作区，支持：
   - 文生图
   - 基于已上传图片编辑
   - 基于当前图片工作台会话已有 artifact 继续编辑
3. 右侧或下方为结果区，展示：
   - 最新结果预览
   - 当前会话图片历史
   - 快速“继续编辑 / 打开产物工作区”动作
4. 页面底层继续使用 session + artifact 作为存储上下文，以复用现有图片接口与 artifact 生命周期；但该页面持有独立图片工作台 session，交互语义以“图片工作台”为中心，而不是聊天转录。

## Complexity Assessment
- Atomic steps: 6+ → +2
- Parallel streams: no → +0
- Modules/systems/services: 5+ (`App.tsx`, preloadable routes, nav rail, new page, image hooks/components, tests) → +1
- Long step (>5 min): yes → +1
- Persisted review artifacts: yes (`.agentdocs/workflow`) → +1
- OpenCode available: yes → -1
- **Total score**: 4
- **Chosen mode**: Full orchestration
- **Routing rationale**: 该需求横跨导航、路由、页面容器、图片生成链路与测试，且需要保留现有聊天内生图能力不回归，适合按阶段实施并显式跟踪验收点。

## Implementation Plan

### Phase 1: 路由与入口
- [ ] T-01: 新增 `/images/:sessionId?` 预加载路由与页面模块
- [ ] T-02: 在左侧导航新增“图片”入口与图标/激活态
- [ ] T-03: 定义图片工作台页面的 session 进入策略（已有 session / 新建 session）

### Phase 3: 收口与验证

- [ ] T-10: 跑 Web 端 typecheck 与目标测试，记录边界限制与剩余事项

## Notes
- 当前确认方案是“专用图片工作台页面 + 独立图片工作台 session + 继续复用 session/artifact 后端模型”，而不是单独发明一套 image-project 存储。
- 若后续需要 mask、多图编辑、批量变体，建议在此页面继续演进，而不要再塞回 `ChatPage` 主输入区。
