## Solution Design
### 1. 不可变业务原则
- 聊天历史与当前会话摘要可按既有策略保存，但不是正式长期记忆；不得从摘要自动晋升为跨会话信息或规则。
- 所有模型/后台发起的新增、修改、合并、启停、归档、范围提升和规则变更，必须先展示准确内容及范围，再获得本次明确确认。
- 不提供“高置信自动保存”模式；`yolo`、自动批准、永久工具授权、开关开启和“开始提取”均不构成逐项确认。
- 手工表单完整展示内容与范围后点击保存，可作为该次明确提交，不二次弹窗；客户端 `confirmed:true`、`source:manual` 或单纯 HTTP PUT 不是证明。
- 群内“好的”、沉默、继续任务、超时都不确认；第一版统一使用登录确认页，尚不支持自然语言批准和平台回调批准。
- 临时/本次/试验性要求、工具输出、执行流水默认不提议；“记住”生成待确认项，不表示已经保存。

### 2. 来源、范围与读取
- 规范 `scopeType + scopeId`：user、workspace、channel_chat、session；团队维持显式 team scope，不折叠进个人范围。
- scope 标识使用服务端归属 ID；channel_chat 包含渠道实例与 chatId，workspace 使用规范工作区身份，禁止模型自报身份即获授权。
- 入站持久化 provenance，绑定内部 message/request：owner、平台、渠道实例、chatId、规范 chatType（未知记为 unknown）、senderId、platformMessageId、时间；使用平台 ID 去重。
- 渠道默认只读当前对话已批准记忆；项目记忆需显式授权，owner 个人记忆默认不注入；写入与读取权限分开。
- 相似比较、查重、唯一键与注入均受相同 scope/owner/team/role 约束；子代理沿祖先链继承来源，不能派生个人会话绕过确认。
- 来源审计按需保存平台标识，不复制整段聊天；敏感内容在候选落库前扫描，凭据等直接拒绝。

### 3. 存储与状态机（建议新增，名称可在契约任务中定稿）
| 实体 | 关键字段/约束 |
| --- | --- |
| 正式 memories | scope、revision、active/archived/superseded、confirmedAt、来源引用；历史兼容 enabled 映射，不双重状态漂移 |
| `memory_proposals` | action、规范 payload/digest、来源、目标及 expectedRevision、过期时间、策略版本、status；候选也属于短期持久化数据，不注入模型 |
| `memory_revisions` | 完整前后版本或可还原快照、操作 ID、确认人、时间、替代关系；新增全局单调 changeSeq 供增量扫描 |
| `memory_jobs` | kind、owner/scope、输入水位/版本集、幂等键、租约 owner/token、重试、费用、状态 |
| `memory_deliveries` | 提议/整理报告通知 outbox、目标、冻结的安全文案、幂等键、重试状态 |
| 来源及审核记录 | 消息来源、决定、保留原状的指纹；scope+条目版本集合+建议内容指纹抑制重复建议 |
- proposal：pending → applied/rejected/expired/cancelled/conflicted；纯 DB 变更在同一事务校验、消费决定、写版本/正文/outbox，失败不留下虚假成功。
- 拒绝/过期默认 7 天内清理候选正文，仅留最小审计摘要；pending 默认 7 天有效，可配置并在界面说明。
- job：queued → running → succeeded/retry_wait/failed/cancelled；领取和续租需 CAS + fencing token，旧 worker 不得迟到提交。
- 同一 scope 正式变更串行或 CAS；人工编辑与维护任务并发必须冲突检测，而不是最后写入覆盖。

### 4. 统一提议、确认与提交
- 建议新建 `memory/memory-governance-service.ts` 及独立 authorization/proposal/commit 模块，存储原语仅由可信提交器调用。
- 自动提取、HTTP extract、工具 add/update/delete、团队初始化只产生提议；重复 upsert 实现删除或委托；手工 CRUD 进入明确人工提交路径。
- 第一版不新增可无人值守调用的正式写入 API：旧 JWT CRUD 变更采用 preview/decision 协议或需要服务端签发的一次性操作；机器调用只能提议，兼容性变化须公告。
- 预览票据绑定 JWT 主体、action、完整内容摘要、scope、目标 revision、nonce、有效期；服务端重新计算摘要和权限，不能自比自或信任客户端标记。
- 拒绝/接受必须关联具体 proposal；允许逐项选择。批量报告每项独立原子提交，明确部分成功与冲突，不声称整批已成功。
- 提案一经展示不可原地变更；“修改后保存”生成新版本并重置确认，未授权管理员、extension admin 不自动获得记忆审批权。
- 拒绝/仅本次使用抑制相同输入版本下的重复询问；不停止当前任务，不自动唤醒 Agent 反复催促。
- 正式条目回滚也作为新变更，经当前 revision 校验和确认后执行；历史不直接改写。

### 5. 周期整理与会话摘要
- 在 `index.ts` 迁移完成后的后台注册区使用 backgroundScheduler；沿既有 stopAll/closeDb 顺序关闭，任务有截止时间、取消信号和有界批次。
- 建议默认启用本地每日巡检；语义整理首次需用户启用并告知模型/费用，启用不代表批准其修改。
- 每日轻巡检：过期候选清理、精确重复检测、结构异常和到期复核，不需要 LLM，不变更正式记忆含义。
- 每周增量语义整理：按 changeSeq 水位取变化条目及同 scope 相关条目；无变化跳过。每月分 scope 分页全量复核，沿游标续跑。
- 调度用持久化 nextDueAt/周期键，初始按 UTC 间隔每日/7日/30日，可配置；停机后每种最多合并补跑一次，禁止补跑洪峰。
- 初始预算建议：全局语义任务并发 1、同 scope 1；单批最多 100 条/输入 12000 tokens/输出 2000 tokens，每用户每天最多 3 次语义请求，均为可配置上限。
- 仅将 scope 内批准正文及必要条件交给无工具的结构化生成调用；不启动普通 cron Agent、不递归触发整理，不发送敏感原始日志。
- 每次检查使用输入版本快照，schema/来源/范围复核后保存结果；候选、报告、任务水位原子提交，水位表示已检查而非用户已批准。
- 检测重复、冲突、临时误入、碎片；不能按更新时间/置信度选真值，不能按未使用天数归档，不能摘要套摘要丢失例外。
- 合并、纠错、归档、替代即使完全重复也只生成建议；后台不得永久删除正式记忆。
- 无问题不通知；新建议每 scope 最多每日汇总一次。已拒绝/保留原状且内容未变不重复提醒；权限撤回、scope 删除、候选失效均终止相关任务。

### 6. 交互、通知与规则
- Web/桌面记忆设置新增待确认、整理报告、历史/回滚；展示原文、建议、理由、来源、范围和完整 diff，默认不勾选实质变更。
- apps 仅经 `packages/web-client/src/infra/memories.ts` 访问；包入口导出 DTO；桌面复用 Web，手机浏览器确认页必交付。
- 原生移动端首期修正现有 stats/settings 解包、提供待办与安全跳转，不宣称拥有完整原生管理界面。
- 渠道通过专属 outbox 发送无敏感正文的通知和无凭证链接；GET 不批准，登录后才可获取 nonce。无公开地址则提示设置页，不伪造链接。
- 投递至少一次，成功发送未 ack 可能重复；同 proposal 通知重放不重复写入，不向错误群或失去授权的目标补发。
- 规则阶段先交付 DB 权威的结构化渠道约定；规则文件以展示目标路径/旧 hash/新 hash/diff 的独立提案发布。
- 文件发布使用受限路径、符号链接防护、同目录临时文件原子替换、DB outbox 与 hash 核验恢复；FS 与 DB 不可假设一个事务。
- 未验证普通 edit/patch/bash 等写入旁路及 workspace 规则加载前，不开放渠道规则文件写入，不声称全局 AGENTS.md 已受审批强制保护；现有用户自主文件编辑不在本期全面接管。
- 规则快照默认当前轮不热换；成功发布后提示下一轮显式刷新或新会话生效，失败只报未应用，不报已生效。

### 7. 迁移、灰度与退出
- 先部署 fail-closed 写入门：未接确认 UI 时停止后台正式写入，仍可聊天及压缩；不允许关闭新功能就回退旧自动写入。
- 旧 memories/user_memory_md 保留且标为 legacy 来源，不能伪造已确认；未知来源不推断为某群，渠道不注入 owner 私人 legacy 记忆，个人原有读取兼容。
- 用显式迁移回填 scope、revision 和 changeSeq，旧索引先检查冲突再替换；旧库升级/重复 migrate/中断恢复均测试；禁止只改 CREATE TABLE。
- 用户明确时间限制的记忆可配置 validUntil；到期停止注入的语义必须在原确认时说明，否则到期只发复核建议。
- 先小范围开启候选和人工确认，再开启周期语义分析，最后开放规则建议；监控正式无确认写入数（必须0）、冲突/重复提议、失败/重试、费用及通知频率。
- 回退关闭提议生成/语义任务/通知，保留已批准版本和只读历史；不删除新表、不降级到可绕过确认的旧二进制，先备份。

**过程中被测试抓出并修复的真实缺陷**：

1. **重启即崩库（严重）**：`migrate()` 里旧唯一索引 `idx_memories_user_type_key` 的 `CREATE UNIQUE INDEX IF NOT EXISTS` 仍保留。首次启动后该索引被 DROP，一旦用户在不同作用域下存在同 type+key 的启用记忆（作用域化索引允许），**第二次启动会真的去重建旧索引并抛 UNIQUE constraint failed，整个迁移失败、网关起不来**。已删除该建索引语句，改为「旧索引只允许被 DROP，永不允许被重建」，并由迁移用例锁定。
2. **显式创建被静默丢弃**：临时语义过滤原本会拦掉 `origin: 'api'` 的显式提交，导致用户在界面新建名为「临时规矩」的规则时只得到 400 而无解释。已把 `api` 与 `manual_extract` / `tool` 一同列为「用户主动发起、不看临时词」。
3. **团队人工写入被误改成提议**：`POST /team/workspaces/:id/knowledge` 是 JWT 鉴权后用户在团队界面点击的人工动作，把它也变成待确认等于对同一动作问两遍。已改回经治理提交器的人工保存路径（仍带 revision/审计），并把 `source` 保持为既有 `auto_extracted` 标签；只有 `team-init-runner` 的自动路径保留提议化。

4. **团队知识入口一度绕开治理提交器**：`applyManualMemoryChange` 的 create 分支无条件写死 `source: 'manual'`，把调用方指定的来源静默吞掉。团队工作区知识路由依赖 `source`（图谱的来源筛选与「自动/抽取」语义词），为保契约曾被改成**直写 `createMemory`/`updateMemory`**——那条入口因此没有 `memory_revisions` 审计记录、无法回滚。
   **最终修法**：提交器改为「仅在调用方未指定来源时回落 `manual`」（人工属性仍由 `confirmationKind: 'manual'` 独立表达），团队路由切回提交器并透传 `source: body.source ?? 'auto_extracted'`。两条不变量由新增 `memory-manual-commit-source.test.ts`（4 例）钉住：来源透传 + create/update 都写 revision；同时修正了「update 失败后继续落库创建重复条目」的隐患。
