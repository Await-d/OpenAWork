# OpenAWork 派工助手实施方案

## Task Overview

对标 Mira Bot 的公开交互，用 OpenAWork 的设计和执行能力实现完整闭环。用户用自然语言提出目标，检查并确认拆分，在「事项」里跟踪各助手，进入原执行会话追问，并在派工入口收到结果。

**首期规划假设**为 Web＋桌面、单个 TypeScript 网关、个人事项、授权工作区内只读分析。首期从 1～5 个独立事项开始，默认每用户同时运行 2 项、单网关 4 项（可配置，联调后校准）。从受控模板或现有 Agent 选择执行助手，确保它支持服务端工具限制。首期交付文本摘要、完整会话及授权的来源引用。团队共享、原生移动、定时触发、跨网关接管与并行写入分期评估。

## Solution Design

### 用户流程与交互契约

1. **派工助手**。用户选择工作区和自然语言请求。规划模型只拿到这条请求及已授权的助手描述，返回经 Zod 校验的事项标题、目标、验收条件和建议助手。网关验证助手引用并返回草稿。文本不清楚时要求补充，规划失败时保留输入。这里的规划可能产生模型费用。
2. **预览确认**。逐项编辑、增删或换助手。显示执行位置、只读范围和事项数量。主操作使用「确认并派工」。提交过程中禁用重复交互，网络不确定时原样重试同一确认请求。
3. **事项列表**。侧栏「事项」提供「待处理」「进行中」「已结束」筛选和回到来源对话的入口。桌面宽屏采用事项列表＋详情，375px 可从列表进入独立详情并保留返回位置。派工入口显示由服务端决定的批次状态和成功数量。
4. **事项详情**。展示目标、验收条件、当前状态、尝试记录、结果摘要和已授权的原文。任务进行中可按已验证的语义排队追问。等待提问时优先展示既有问题组件，回答会回到原尝试。成功后继续追问使用同一子会话的新轮次，保留已完成的原结果。失败或中断时可单项重试，保留旧尝试记录。
5. **结果交付**。按已持久化状态生成汇总卡，任务异常会显示「部分完成」或具体终态。信息通知携带事项链接，复用信息类通知口径。确认通过的本轮任务以服务端真实状态为准，状态文本和颜色同时表达。界面沿用 Nebula token，并验证键盘焦点、加载、空态、断线和错误态。

### 数据模型与状态归属

| 记录 | 最小字段及约束 |
| --- | --- |
| `dispatches` 派工单 | `id`、`ownerUserId`、`workspaceRef`、`originSessionId`、可选 `originMessageId`、标题、草稿内容及 `revision`、`confirmedAt`、时间戳。工作区和原会话归属由服务端解析。一个草稿至多确认一次，确认内容带摘要用于精确重放。 |
| `dispatch_items` 事项 | `id`、`dispatchId`、顺序、目标、验收条件、确认的助手引用及非敏感配置快照、`currentAttemptId`、时间戳。`(dispatchId, ordinal)` 唯一，列表按归属与更新时间游标分页。 |
| `dispatch_attempts` 执行尝试 | `id`、`itemId`、尝试编号、动作键、运行请求键、子会话引用、状态、停止标记、起止时间、结果摘要、错误类别。`(itemId, attemptNo)` 唯一，入队索引覆盖状态、排队时间和稳定次序。执行请求键全局唯一，子会话和运行结果的组合可用于对账。 |

首跑为每个事项建独立子会话。正常追问沿用该子会话并追加尝试，每个尝试有独立执行请求键。失败或中断后的「重试」开启新会话，保留前次执行记录。详情深链接在事项下切换当前和历史尝试。完成时保存有界文本摘要和授权引用，完整消息以会话为准。来源会话被删除时显示「来源不可用」，子会话被删除时显示「原文不可用」。实施前核对现有删除和账户清理契约。

**执行状态**为 `queued → running → succeeded | failed | interrupted | cancelled`。受支持的提问会 `running → waiting_user → running`。运行中取消先记录停止请求，待执行结束确认后才进入 `cancelled`。队列中的取消在事务内立即完成。首期等待回答时保留并发槽，恢复前校验归属。超时后结束尝试并提示用户重试。批次按当前尝试聚合，活跃和待处理优先于终态。全部成功显示「已完成」，有成功及其他终态显示「部分完成」，无成功时根据失败、中断或全部取消显示原因，保留逐项统计。

### 网关接口与幂等

| 路由建议 | 行为 |
| --- | --- |
| `POST /dispatches/drafts` | 校验会话、工作区和可用助手，生成含 `dispatchId`、`revision` 的草稿。 |
| `PATCH /dispatches/:id/draft` | 按 `revision` 保存修改。过时版本返回 `409` 并允许客户端重新加载。 |
| `POST /dispatches/:id/confirm` | 校验版本、权限和容量。在同一事务内确认草稿、创建事项及排队尝试。相同已确认修订和规范化内容返回同一批次。同一确认标识对应不同有效输入返回 `409`。 |
| `GET /dispatches`、`GET /dispatches/:id` | 读取拥有者可见的列表或详情，返回子项状态、版本、摘要和受控引用。会话与产物权限单独验证。 |
| `POST /dispatches/:id/items/:itemId/{follow-up,cancel,retry}` | 按当前尝试版本校验，使用现有待发能力或唯一的事项级等待槽。刷新重发沿用同一动作键。动作键须用安全随机源或服务端签发。 |

所有接口用现有认证和 Zod 输入校验。访问不到的事项统一 `404`。对队列限额给出可重试的容量错误。Web 与桌面经 `@openAwork/web-client`，`packages/shared` 只放传输契约。首期由详情快照保证断线恢复，活动页采用可见性门控的轮询或现有事件提示后重拉。事件丢失时仍可读取准确状态。

### 执行、恢复与权限

- **启动**。事务内认领排队尝试并持久化运行请求键，提交后调用已验证的后台执行入口。启动与结算都绑定当前尝试。按用户和网关限制并发，每用户设队列容量，达到上限时给出反馈。对并发槽的所有释放统一测试。
- **对账**。网关启动扫描排队和在途记录。排队项可以继续。已认领项按执行请求键核实终态或有效暂停事实，找不到可信依据时标为「中断」。模拟进程在认领后、启动后和执行完成但事项未结算时退出。旧轮次的迟到结算只允许更新自己的审计记录，保留当前尝试和取消状态。
- **交付**。先保存结果，再按批次和完成轮次投递去重的结构化回告。复用现有通知和准入机制，记录可补投状态。信息通知只承担提醒职责，回告不触发无上限的父会话续跑。前端按服务端版本更新，迟到响应无法回退状态。
- **权限**。创建、确认、认领、续聊、恢复及结果读取都使用真实发起人上下文和规范化工作区范围。规划模型只有结构化输出能力。首轮启动前为专用会话登记服务端只读策略，普通会话元数据编辑与恢复不会修改它。每轮使用同一策略过滤工具声明并约束实际执行，策略缺失或无效时停止该轮。只允许经验证的工作区读、列举、搜索和受控提问。统一屏蔽任意命令、写入、网络工具、任意 MCP、递归委派和其他会话访问。保护路径、安全配置、工作区边界和模型提供方授权均沿用项目既有规则并单独测试。只读约束的是工具动作，选择外部模型仍涉及相应模型的数据传输。
- **收口**。复用既有提问生命周期，验证等待、回答、取消与超时的通知状态能在网关重启后对账。若重启后无法恢复有效提问，将尝试标为中断并收口待处理通知。对恢复中的权限变化和失去工作区的尝试输出可读的状态原因。仅当网关仍在线时，在客户端关闭后继续工作。

## Notes

### 验收与上线

| 验收点 | 可观察证据 |
| --- | --- |
| 用户确认和并行 | 草稿未确认时执行调用为 0。确认后两个事项可同时运行并各有一条会话。双击确认或跨端重试只创建一次。 |
| 单项续聊与结算 | 追问甲使用甲的子会话，乙不收消息。追问期间保留甲的旧结果。一项失败时显示部分完成，只重试该项。 |
| 容量、取消与提问 | 并发占满的任务排队。在运行中取消等到真实停止后释放槽位。暂停和恢复遵守上限，通知待办随回答或终止正确收口。 |
| 故障恢复 | 浏览器断开后且网关在线时继续。桌面完全退出触发本地网关停止时提示用户，恢复后排队项可继续，终态可对账，未知在途记为中断。重复回告不会改变事项事实。 |
| 访问控制 | 两账户交叉访问、助手失效、工作区授权撤销、只读能力约束均做服务端回归。敏感数据、完整提示和文件内容不进入运行日志。 |
| 发布准备 | 新增与回归 Vitest、网关和客户端类型检查及构建，显式运行 Web 测试，再跑 Web／桌面 Playwright。日志至少记录运行关联、状态转换和错误类别。功能开关默认关闭。关闭期间拒绝新确认、追问和重试，暂停认领既有排队项。执行中的任务在预算内结算，历史和取消入口继续可用。重新启用后调度剩余队列。 |

### 实施恢复记录

- 网关仓储与页面子任务分别遇到 504 和 503。恢复时已存在共享契约、输入校验及数据库迁移，仓储与页面尚未落盘。
- 首个可验证版本先处理用户主动粘贴的文本。网关采用独立无工具生成入口，固定所选模型，保存事项历史供追问。工作区读取、普通聊天子会话、提问暂停和通知中心接入仍按原方案单独验收。
- 依赖顺序为仓储 → 执行器 → 路由联调 → 跨端验证。页面与客户端可按现有契约并行开发。

### 个人文本版本现状

- Web 和桌面共用 `/dispatches` 页面，调用 TypeScript 网关的 `/dispatch-assistant` API。用户粘贴文档摘录，生成并编辑草稿，再确认当前已保存的修订版本。确认后，网关把事项写入 SQLite 队列并并行处理。页面展示单项结果和历史，并提供追问、重试和取消。
- 执行使用草稿绑定的账户聊天模型。规划阶段发送目标，执行阶段发送文档摘录和该事项所需的历史。执行器只生成文本。事项有独立的历史记录。工作区读取、普通聊天子会话、等待用户提问和通知中心仍属于原方案的待验收范围。

### 前端视觉优化

先用真实 Chromium 在暗/亮 × 375px/1440px 渲染列表页与详情页，逐张截图评估，再按发现的问题改，改后复测对比度。

- **状态可辨识**：新增 `dispatch-status-badge.tsx`，状态改为「圆点 + 文案」徽标。文字统一用 `--fg-strong`、语义色只落在圆点/背景/边框——实测亮色主题把主题色当小字文字色只有 3.0～4.05，达不到 WCAG AA。运行中/排队中/部分完成归 active（琥珀），已完成为 done（靛青），失败/中断为 alert（珊瑚），草稿/取消为 idle（中性）。`running` 圆点带呼吸动画，`prefers-reduced-motion` 下关闭。
- **消除误导文案**：`dispatchProgressLabel` 让草稿态显示「N 个事项待确认」而不是「0/0 项完成」；详情页未加载时不再显示列表页说明；事项区标题从重复的「1/3 项完成」改为「N 个事项」。
- **消除状态歧义**：事项卡头部原本同时显示事项徽标与执行记录徽标，会出现「事项运行中 + 记录已完成」并排。现在状态只在执行记录上出现一次，事项头只保留角色 chip。
- **列表可扫读**：记录行改为「标题 + 进度」左列、徽标右列的网格，相邻行加 `border-subtle` 分隔；进度文字提到 `--fg-default`（`--fg-muted` 在 elevated 背景上仅 4.42）；两列比例由 3:2 调成约 1:1.05，记录区不再被新建表单压成附属。
- **首屏密度**：详情页把模型说明与数据披露收进两级 `<details>`，头部只留标题 + 状态 + 一行元信息；草稿编辑的「事项 N」图例补上事项标题，便于多事项定位。
- **操作层级**：移除事项、取消事项改 `dispatch-danger`（珊瑚描边）；空输入时「发送追问」直接禁用；确认区改 sticky 并在编辑区留 5rem 尾部空白，滚到底不被悬浮面板遮住。
- **验收脚本**：新增 `apps/web/harness/verify-dispatch-visual.ts`，对暗/亮 × 375/1440 × 列表/详情的 24 项断言（文字对比度 ≥4.5、无横向溢出、按钮高度 ≥28px）全部通过。派工前端定向测试 7 项通过，Web 类型检查与生产构建通过。截图存于 `apps/web/harness/dispatch-visual-artifacts/`。
- **已知取舍**：「运行中」与「部分完成」同为琥珀（同属在途语义），需读文字区分——这是不靠颜色单独传达信息的有意设计。列表行分隔线仍偏淡，属 `border-subtle` 的设计刻度，未为此破例提升。

### 真实上游链路端到端（不 mock 派工代码）

此前所有派工测试都 mock 掉 `planDispatch` / `generateDispatchResult`，只验证路由与队列。本轮新增 `services/agent-gateway/src/verification/verify-dispatch-upstream-e2e.ts`，**只替换最底层的 `fetch`**，让请求真实穿过：

`getChatProvider` → `getProviderForSelection` → `resolveModelRouteFromProvider` → `runUpstreamGenerate` → fetch → 结算

流程与断言（4 条全过）：

1. 走真实 `PUT /settings/providers` 配置一个指向模拟上游的 provider（`type: openai` + 自定义 `baseUrl` + `chat_completions`）。
2. `POST /drafts` 触发**真实规划调用**，返回经 Zod 校验的草稿；草稿阶段事项数为 0。
3. `POST /confirm` 真实入队，真实调度器认领并调用上游，`status` 走到 `succeeded`，结果等于上游返回文本。
4. 追问沿用同一线程：第二次执行请求携带追问内容与前次结果。
5. 请求体断言：**规划只带目标、不带摘录**；执行带摘录与事项目标；两次请求都打到配置的 provider；两阶段都不声明工具。

**顺带纠正一处认知**：`runUpstreamGenerate` 在无工具时**省略 `tools` 字段**（并非发空数组），所以断言改为「解析后 `tools` 为空或不存在」，比字符串匹配稳。

**边界**：上游返回的是固定 SSE 帧，验证的是「链路 + 请求形状 + 状态流转」，不等于真实厂商模型的质量与协议差异验收。

**仍待真实环境**：真实厂商模型联调（需有效模型凭据）与桌面 WebView 实机验收，当前环境两者都不具备。
